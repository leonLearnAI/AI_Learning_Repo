## 7.2 本周深化的重点:消息队列四方选型与 Step Functions(Day 15–16)

**① 消息与事件四方选型(Day 15)**
- **SQS**:一条消息只被一个消费者处理一次,靠**可见性超时**防止重复认领,处理失败会**自动重新出现**等别人捡起来(所以处理逻辑要设计成幂等);标准队列高吞吐但不保证顺序,FIFO 队列保证顺序但吞吐有限;反复失败的消息交给**死信队列(DLQ)**隔离排查
- **SNS**:一对多广播,但**没有暂存重试能力**,推送失败基本就丢了;**SNS 扇出到多个 SQS** 是经典组合——SNS 补上 SQS"没法一对多"的短板,SQS 补上 SNS"没法重试"的短板
- **EventBridge**:比 SNS 多了**按内容做条件路由、Schema Registry、定时触发、接第三方 SaaS**这几项能力,是"带智能路由的升级版 SNS"
- **Kinesis**(严格来说属于"分析"模块,但这周和消息队列放在一起对比讲):和前三者最本质的区别是**数据不会因为被消费就消失**,默认保留 24 小时(最长 365 天),多个消费者可以各自独立、重复读取,专门服务"同一份数据需要被多方完整读取甚至回放"的场景

**② Step Functions(Day 16)**
- 六种基本状态:Task(干活)、Choice(分支)、Wait(等待)、Succeed/Fail(终止)、**Parallel**(几个数量固定但逻辑不同的分支同时跑)、**Map**(同一套逻辑套在一个数量不确定的数组上,数据量特大时用**分布式 Map**)
- 标准工作流(按状态转换次数计费,精确执行一次,最长跑 1 年,支持人工审批回调)vs 快速工作流(按执行次数+时长+内存计费,至少一次执行,最长 5 分钟,吞吐更高)
- **人工审批断点**靠 `.waitForTaskToken` 回调等待模式实现,**只有标准工作流支持**,因为快速工作流 5 分钟的上限跟"可能要等好几小时"这件事天然冲突
- **该用 Step Functions 还是 Agent**:流程能在设计阶段完全想清楚"先做什么、遇到什么情况走哪条分支"→Step Functions(便宜、快、可预测);下一步该做什么得让模型临场判断→Agent(贵、难预测,但能应对无法枚举的场景)

## 7.3 架构图/流程(文字描述)

**Parallel vs Map 的区别**
```
Parallel:几个数量固定、逻辑不同的分支同时跑(比如"提取文字"和"生成缩略图"同时开始)
Map:同一套逻辑,套在一个数量不确定的数组上(比如50份文档,每份都跑一遍同样的处理流程)
```

**"上传文档→提取→检测PII→生成摘要→存库"状态机**
```
Task(提取文字) → Task(检测PII)
  → Choice判断:检测到高敏感信息?
      → 是:进入回调等待(生成任务令牌,等人工审批,SendTaskSuccess后继续)
      → 否:直接往下走
  → Task(生成摘要) → Task(存库) → Succeed
```

**SNS 扇出到多个 SQS**
```
发布者 → 发一次消息给 SNS → SNS 复制消息,分别投递给挂在它下面的多个 SQS 队列
→ 每个队列后面站着一个独立系统(库存/邮件/财务),各自按自己的节奏处理、失败自己重试,互不干扰
```

**案例**:一家零售企业把多年的销售数据整理好加载进 Redshift,分析师可以对几十亿行数据做复杂的多维度聚合分析,查询响应速度比直接在 S3 上用 Athena 查快得多。

## 8.2 本周深化的重点:数据湖工程与向量检索(Day 17–18)

**① 数据湖、Glue 与 Athena(Day 17)**
- 数据分层 **Raw(原样留底)→ Bronze(格式统一)→ Silver(业务清洗,能直接分析)→ Gold(聚合建模,直接能用)**,数据质量一层比一层高,数据量往往一层比一层小(聚合导致的,不是清洗导致的)
- **Parquet 按列存储**,能跳过不需要的列,同类型数据压缩率也更高,比 CSV(行存)又快又省
- **Glue 三件套**:Crawler(认路,扫描数据生成表结构)→ Data Catalog(记路,存元数据不存实际数据)→ ETL Job(搬东西,真正处理数据,处理完常需再跑一次 Crawler 更新目录)
- **Athena 按扫描量计费**:分区跳过不相关文件夹 + 列存跳过不相关列,**两层优化是相乘关系,不是相加**,叠加起来能把账单压缩到千分之一甚至更低
- **RAG 数据清洗五步**:①采集/摄入 →②文本提取(格式统一)→③清洗与去重→④敏感信息处理(PII检测/脱敏)→⑤结构化与元数据打标(部门/日期/权限,方便过滤和多租户隔离)

**② 向量检索与 OpenSearch(Day 18)**
- **Embedding** 把文本变成坐标点,意思相近的词坐标离得近;**余弦相似度**只看方向不看大小,是文本检索最常用的度量方式
- 数据量大时精确匹配太慢,用**近似最近邻(ANN)**换速度;**HNSW** 靠多层"路网"(上层稀疏快速跳转,下层密集精细定位)实现又快又相对精确
- 语义检索有盲区——**专有名词、精确编号、具体数字**这类内容不适合被语义化(容易被相邻年份/编号"稀释"),该用 **BM25 关键词匹配**死磕字面,和向量检索**混合使用**取长补短
- **OpenSearch Serverless 的 OCU 有最低计费门槛**,哪怕没有流量也要为保留的最低 OCU 数量持续付费,这也是为什么很多企业转而选 Aurora + pgvector 做向量库

## 8.3 架构图/流程(文字描述)

**RAG 数据清洗五步**
```
①采集/摄入(Raw层)→②文本提取(格式统一,对应Bronze层)
→③清洗与去重(去掉噪音、重复内容)→④敏感信息处理(PII检测/脱敏)
→⑤结构化与元数据打标(部门/日期/权限标签,方便后续按条件过滤和多租户隔离)
```

**Athena 成本优化的两层叠加**
```
无分区的CSV,查一天的数据 → 全量扫描,扫描量=数据总量
按天分区的Parquet,查一天的数据 → 先靠分区跳过其他363天(只剩1/365的数据量)
→ 再靠列存跳过不需要的列(进一步压缩) → 两层效果相乘,不是相加
```

**多账号治理三件套**

**案例**:一家大企业用 Control Tower 统一搭建多账号环境的护栏规则,团队新建资源时只能从 Service Catalog 里选审批过的标准模板,同时定期看 Trusted Advisor 的建议清单去优化闲置资源。

## 9.2 本周深化的重点:可观测性三件套(Day 19)

- **CloudTrail**:记录"谁对 AWS 资源做了什么操作"(控制面审计),不关心业务逻辑
- **CloudWatch Logs**:记录"程序自己打印了什么"(应用层业务日志),不关心有没有调 AWS API
- **X-Ray**:把一次请求经过的所有服务串成一条完整链路,**Trace(整趟旅程)包 Segment(每一站)包子分段(某一站内部更细的动作)**
- **CloudWatch 五件套分工**:Logs(存原始文本)、Metrics(存数值型指标,是分类容器不是具体指标本身)、Alarms(盯着 Metric 触发告警)、Logs Insights(交互式搜索日志)、Dashboard(拼成可视化大屏)
- **LLM 应用特有指标**:TTFT(首字延迟,衡量"感觉有没有立刻开始动")、Token 用量、成本归因、拒答率、错误/重试率
- **Bedrock 的 Model Invocation Logging** 默认关闭,记录每次调用的完整 prompt/返回内容/模型/token 用量,是排查问题和做合规审计的第一手数据

## 9.3 架构图/流程(文字描述)

**三个可观测性工具的判断依据**
```
谁动了 AWS 资源(操作审计) → CloudTrail
程序自己说了什么(业务日志) → CloudWatch Logs
一次请求走了哪几步、每步花多久(链路追踪) → X-Ray
```

### ★★☆ Kiro
**AWS 的智能体化(agentic)IDE**

Kiro 是 AWS 2025 年推出的新一代开发工具,定位是"agentic IDE"——不只是像传统 AI 编程助手那样帮你自动补全代码,而是能理解更大范围的项目上下文、自主拆解和执行多步骤的开发任务(比如"实现这个功能"背后涉及的建文件、写代码、写测试、跑测试这一整套流程)。

**案例**:一个开发者让 Kiro"帮我实现一个用户注册接口,包含输入校验和单元测试",Kiro 能自主规划出需要修改哪些文件、写哪些代码、生成对应测试,而不只是补全当前正在写的这一行代码。

### ★★☆ Amazon Q Developer
**AI 编码助手**

Amazon Q Developer 是 AWS 的 AI 编程助手,集成在主流 IDE 里,提供代码自动补全、代码解释、根据自然语言描述生成代码、自动化代码审查和安全漏洞扫描这些能力,定位上更接近"代码编写和审查阶段的智能助手",跟 Kiro 那种"自主执行整个开发任务"的定位不完全一样。

**案例**:一个开发者在 VS Code 里装了 Q Developer 插件,写代码时它会实时给出补全建议,提交代码前它还能自动扫描出潜在的安全漏洞和不规范写法。

### ★★☆ CodePipeline / CodeBuild / CodeDeploy
**AWS 原生的 CI/CD 三件套**

这三个服务分别负责持续集成/持续交付流程里的不同阶段——CodePipeline 负责编排整条流水线(代码提交后依次触发构建、测试、部署这几个阶段);CodeBuild 负责编译代码、跑测试、打包;CodeDeploy 负责把构建好的产物实际部署到 EC2、Lambda 或 ECS 上。三者组合起来是一整套从代码提交到自动上线的流水线,不过实际工作中很多团队还是更常用 GitHub Actions 这类第三方工具。

**案例**:一个团队配置了一条流水线,开发者把代码推送到代码仓库后,CodePipeline 自动触发 CodeBuild 编译和跑单元测试,测试通过后 CodeDeploy 自动把新版本部署到生产环境,全程不需要人工干预。

### ★★☆ AWS Amplify
**前后端一体化的快速开发平台**

Amplify 让你能快速搭建一整套包含前端托管、后端 API、身份认证(和 Cognito 集成)、数据库这些能力的全栈应用,提供大量开箱即用的组件和 CLI 工具,特别适合快速做 PoC、Demo 或中小型项目,不用手动一项项拼接各个 AWS 服务。

**案例**:一个 FDE 要给客户快速搭一个演示用的 Demo 应用,用 Amplify 几个命令就能拉起前端托管、Cognito 登录、后端 API 的完整雏形,几小时内就能给客户演示,不用花几天时间手动搭建每个组件。

### ☆☆☆ AWS CodeArtifact / AWS Cloud9
**包管理与云端 IDE(优先级较低,可跳过)**

CodeArtifact 是一个托管的包/依赖仓库服务(类似私有版的 npm/PyPI 仓库);Cloud9 是一个基于浏览器的云端集成开发环境。这两个在 AI 工程师/FDE 的日常工作里出现频率不高,阶段一可以直接跳过,了解存在即可。

## 10.2 本周深化的重点:IaC 三选一(Day 20)

- **声明式(描述目标状态)vs 命令式(描述操作步骤)**:声明式工具自动对比现状和目标状态、只执行差异部分,具备**幂等性**,可以反复安全执行;命令式脚本重复跑容易因为"已存在"而报错或重复创建
- **CloudFormation**:Stack 管理一整套资源的生命周期;**变更集**在真正执行前预演"会新增/修改/删除什么";**漂移检测**发现绕开 IaC 的手动改动
- **CDK**:用 TypeScript/Python 写基础设施,**最终依然编译成 CloudFormation 模板**,不是独立引擎;L1(贴近底层,什么都要配)、L2(合理默认值,日常最常用)、L3(整套架构模式打包,省事但定制空间小)
- **Terraform**:靠 **Provider** 插件实现跨云能力;靠 **State 文件**记录"现实世界现在长什么样",团队协作场景必须**远程共享存储**,否则多人各自基于过时状态操作会冲突覆盖;靠 **Module** 做复用
- **CDK vs Terraform 不是二选一**:纯 AWS + 团队擅长写代码→CDK;多云或已有 Terraform 积累→Terraform,两者可以在同一个组织里分工并存

## 10.3 架构图/流程(文字描述)

**IaC 工具选择判断路径**
```
需要跨云厂商(AWS+Azure等)或团队已有 Terraform 积累 → Terraform
纯 AWS 环境 + 团队开发者擅长写编程语言 → CDK
只需要原生 YAML/JSON、不需要编程语言复用能力 → 直接用 CloudFormation
```
