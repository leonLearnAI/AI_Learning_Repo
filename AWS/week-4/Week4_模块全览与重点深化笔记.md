### ★★☆ 模型定制四种
**微调 / 持续预训练 / 蒸馏 / 自定义模型导入**

当预训练好的基础模型不能完全满足业务需求时,有四种"定制"手段,各自解决不同问题:**微调(Fine-tuning)**用少量标注数据调整模型的输出风格或格式;**持续预训练(Continued Pre-training)**用海量无标注的领域语料让模型补充某个专业领域的知识;**蒸馏(Distillation)**用一个更强的大模型去"教"一个小模型,让小模型在特定任务上逼近大模型效果但成本更低;**自定义模型导入(Custom Model Import)**把你自己训练好的开源模型权重直接导入 Bedrock 统一管理调用。决策顺序通常是:先看提示工程能不能解决(最便宜)→ 不行看要不要 RAG(补知识,动态)→ 还不行考虑微调(改风格格式)或持续预训练(补领域知识)→ 最后考虑蒸馏降成本。**这也是这四种手段和 RAG、提示工程放在一起时最常被问到的一组易混淆点**:改行为→提示工程,补知识→RAG,改风格格式→微调,补领域→持续预训练,降成本→蒸馏。

**案例**:一家企业想让客服模型的回复风格更贴近自己品牌的语气,用少量标注过的历史客服对话做微调,让模型学会这种特定说话方式,不需要重新训练模型或做工程量大得多的持续预训练。

## 11.2 本周深化的重点:Converse API、模型选型计费与 Tool Use(Day 22–24)

**① Bedrock 主体与 Converse API(Day 22)**
- Bedrock 是"租用"而不是"自建"——把模型部署和运维整体托管给 AWS,按调用量付费换取不用管底层这摊事
- **只学 Converse,不学老的 InvokeModel**——Converse 用统一请求格式屏蔽不同模型家族的差异,换模型只需换 `modelId`
- 一次调用三部分:**messages**(对话历史,模型没有记忆,靠每次重传实现"记得")、**system**(独立的角色设定)、**inferenceConfig**(生成参数)
- 三个推理参数:**temperature**(整体随机程度)、**top_p**(划定累计概率达标的候选范围,不是固定数量)、**max_tokens**(硬性长度上限)
- **ConverseStream**:流式版本,返回一连串事件(消息开始/内容增量/消息结束),后端边收边转发实现打字机效果
- **数据使用承诺**:输入输出不用于训练基础模型,客户第一个必问的问题

**② 模型选型与四种计费(Day 23)**
- 能力、延迟、成本三者永远博弈——先看任务需要多强能力,不是无脑上最强模型
- 输出 token 比输入 token 贵 3-5 倍,因为生成是逐 token 串行计算,读取是并行处理
- 四种计费:**按需**(用量不稳定)、**预置吞吐量**(稳定大流量,且是自定义模型的唯一入口)、**批量推理**(离线任务约五折)、**提示缓存**(固定前缀+高频调用,靠前缀匹配大幅降价)
- 跨区域推理配置文件提升可用性但有数据驻留合规副作用,欧洲客户要先确认路由范围
- 上下文长度对成本的影响是**加速增长,不是线性的**——这也是为什么"检索相关内容"比"塞进全部信息"划算

**③ Tool Use / 函数调用(Day 24)**
- 模型自己不会"动手",只会"准确说出它需要什么帮助"
- 完整往返四步:发工具清单 → 模型提出结构化调用请求 → 代码真正执行 → 结果喂回给模型 → 模型基于结果生成最终回答
- **工具描述写得好不好,直接决定模型会不会用对**——本质是一个语义匹配问题
- 不依赖的工具调用可以并行,有依赖关系必须串行
- 工具执行失败,错误信息也要老实喂回给模型(不是代码自己组织语言回应用户),不然模型要么卡住要么产生幻觉
- **Tool Use 是 Agent 的地基**——Agent 就是把这套"调用→看结果→决定下一步"的循环反复执行多轮

## 11.3 架构图/流程(文字描述)

**一次 Converse 调用的结构**
```
messages(对话历史) + system(角色设定) + inferenceConfig(temperature/top_p/max_tokens)
→ 发给 Converse API → 模型生成回复
(需要流式则改用 ConverseStream,返回事件流,后端边收边转发给前端)
```

**Tool Use 完整往返**
```
①把工具清单+用户问题发给模型 → ②模型判断需要工具,生成结构化调用请求
→ ③你的代码真正执行(调用数据库/外部API)→ ④执行结果(或错误信息)喂回给模型
→ 模型基于结果生成最终自然语言回答
```

### ★★☆ Prompt Management
**提示词的版本化与集中管理**

Prompt Management 让你把提示词从代码里剥离出来集中管理,支持版本控制(对比不同版本效果、随时回滚)、变量占位符(同一模板运行时填入不同变量值),避免提示词像散落的字符串一样硬编码在各处代码里,改一次提示词要满仓库找。

**案例**:一个团队的客服机器人提示词经常需要迭代调整,过去改提示词要改代码重新部署,用 Prompt Management 之后提示词单独管理、单独发版,业务人员不用工程师介入就能测试新版本提示词。

### ★★☆ Prompt Flows
**可视化编排轻量工作流**

Prompt Flows 提供一个可视化拖拽界面,把多个提示词调用、条件判断、数据转换这些步骤像画流程图一样拼接成一个轻量工作流,不需要为这种相对简单的多步骤提示词编排单独写一套 Step Functions 状态机或自己写代码胶水。

**案例**:一个团队想做"先分类用户意图,再根据不同意图调用不同提示词模板生成回复"这样的两步流程,用 Prompt Flows 拖拽几个节点就能搭起来,不用写代码。

### ★★☆ Amazon S3 Vectors
**原生支持向量存储的对象存储,RAG 场景最省钱的选择之一**

> ⚠️ 这一项是 Day 30 总复盘核对"向量库四选一"这组易混淆点时,发现的一处真正的内容空白——阶段一 30 天里完全没有讲过,这里补齐。

S3 Vectors 是全球第一个**原生支持存储和查询向量**的对象存储服务,2025 年底正式 GA。它在 S3 里新增了一种"向量桶(Vector Bucket)"的桶类型,配一套专属 API 存取查询向量,不用自己搭任何基础设施。核心卖点是**便宜**——相比传统向量库方案(比如 OpenSearch),存储和查询成本能降低最多 90%,本质是把"向量检索"能力叠加到了 S3 本身"廉价、海量、免运维"这套特性上。规模上单个索引最多存 20 亿个向量;性能上比 OpenSearch 这类专门优化过的搜索引擎慢一些(查询延迟约 100ms 起,不常查的数据一秒内返回)。它原生和 **Bedrock Knowledge Bases** 集成,可以直接当 Knowledge Bases 的向量存储后端,也能和 OpenSearch 搭配做**分层策略**——海量低频数据放 S3 Vectors 省钱,高性能实时查询的那部分数据放 OpenSearch。

**案例**:一个企业想给 Agent 建立"长期记忆",存下海量的历史交互记录、文档、洞察。如果全用 OpenSearch 存,成本会随数据量线性暴涨;换成 S3 Vectors,能用很低的成本存下十亿级向量,让 Agent 不用被迫"遗忘"旧的上下文。

## 12.2 本周深化的重点:Knowledge Bases、Guardrails 与 AgentCore(Day 25、27、29–30)

**① Knowledge Bases 与分块(Day 25)**
- 完整链路:数据源 → 摄取(分块+生成嵌入)→ 向量存储 → 检索 →(可选)生成
- **四种分块策略**:固定分块(简单粗暴)、语义分块(按话题转折切)、分层分块(跟着文档天然结构)、自定义 Lambda(应付特殊格式)
- chunk size 太小丢上下文,太大稀释语义;**overlap** 兜底"切割点不巧导致信息丢失"
- **Retrieve**(自己拼提示,可控)vs **RetrieveAndGenerate**(一步到位但黑盒)——需要自定义拼接逻辑必须用前者
- **元数据过滤**做多租户隔离和时效性限定;**重排序**靠"先粗召回、再精排"两阶段设计平衡速度和精度

**② Guardrails 与提示安全(Day 27)**
- 五种能力:**内容过滤**(通用安全线)、**拒绝主题**(业务边界,跟内容有害与否无关)、**敏感信息遮蔽**(输入输出两个方向都要配,防的方向不同)、**上下文接地检查**(实时拦截幻觉,跟 Day 26 忠实度评测是同一问题的两种解法)、**自动化推理检查**(硬性逻辑规则校验)
- 提示注入三种手法:直接指令覆盖、角色扮演绕过、**间接注入**(藏在外部内容里,Agent 场景尤其要警惕)
- 防御不能只靠 Guardrails 一层,要叠加系统提示强化、工具最小权限、人工审批、上下文接地检查
- Guardrails(实时对话链路)vs Comprehend(通用文本分析工具)vs Macie(S3 静态数据扫描)——三者工作的"位置"不同

**③ AgentCore 与生产化(Day 29)**
- 七个组件:**Runtime**(Agent 专属常驻托管)、**Gateway**(自动把现有 API 转成 MCP 工具)、**Memory**(托管会话与长期记忆)、**Identity**(Agent 代表用户调下游系统时凭证和权限怎么恰当限定)、**Observability**(为多轮循环执行路径定制的 X-Ray)、**Evaluations**(Agent 行为质量持续量化)、**Policy**(基于 Cedar,管业务层面能不能做这件事)
- IAM 管"能不能碰 AWS 资源",Policy 管"业务上能不能做这件事"——两者可以同时存在,管辖范围不同
- Bedrock Agents(交钥匙但绑定 Bedrock 生态)vs AgentCore(框架无关模型无关,但要自己搭)

**④ Bedrock Evaluations 三种模式(Day 30)**
- **自动化评测**(早期快速迭代,只能评估有标准答案的场景)、**人工评测**(上线前关键把关,最贴近真实用户感受但慢贵)、**LLM-as-a-judge**(上线后持续大规模监控,介于两者之间)
- LLM-as-a-judge 的偏差:偏好更长的答案、位置偏差(顺序影响打分)——靠明确指令、交换顺序取均值、真人抽查缓解

## 12.3 架构图/流程(文字描述)

**Knowledge Bases 完整链路**
```
数据源 → 摄取(分块 → 生成嵌入)→ 向量存储 → 检索(用户提问变向量,做近似最近邻)
→ (可选)生成:Retrieve只返回片段自己拼提示 / RetrieveAndGenerate一步到位
```

**RAG 排查"它答错了"的思路**
```
先看这次检索到的原始内容里有没有正确答案
→ 没检索到相关内容:问题在检索环节(检索不到/检索到错的)
→ 检索到了但回答依然不对/没用上:问题在生成环节(检索到了但没用上/上下文太长被稀释)
```

**AgentCore 生产级 Agent 架构位置**
```
Agent 推理逻辑(Strands/任意框架,框架无关)
├─ Runtime:托管这个 Agent 常驻运行
├─ Gateway:把公司现有API自动转成MCP工具,供Agent调用
├─ Memory:托管会话状态与长期记忆
├─ Identity:Agent代表具体用户调下游系统时的凭证与权限限定
├─ Observability:记录多轮循环的完整执行路径
├─ Evaluations:持续评估Agent的行为质量
└─ Policy(Cedar):业务层面的细粒度授权判断
```

# 模块十三:其他 AI 服务(共 10 项)

## 13.1 全部 10 项内容简介

### ★★★ Amazon Textract
**文档结构化提取**

Textract 自动从扫描件、图片、PDF 这类非结构化文档里,提取出文字、表格、表单字段这些结构化信息,不只是简单的 OCR 文字识别,还能理解表格的行列结构、表单里"字段名-字段值"的对应关系。这是智能文档处理(IDP)场景的核心工具,Day 17 讲 RAG 数据清洗时已经提到过它是"文本提取"这一步的常用工具。

**案例**:一家保险公司需要处理大量纸质理赔单据的扫描件,用 Textract 自动提取出表单里的姓名、保单号、理赔金额这些字段,不用人工一个个录入。

### ★★☆ Amazon Comprehend
**通用 NLP API,含 PII 检测**

*(Day 27 讲 Guardrails/Comprehend/Macie 分工时已展开过,这里不重复——核心记忆点:Comprehend 是通用文本分析工具,不专属 LLM 场景,可以在任何需要分析文本的地方调用)*

### ★★☆ Amazon Kendra
**企业级语义搜索引擎**

Kendra 是一个开箱即用的企业搜索引擎,能连接多种数据源(SharePoint、S3、数据库等),对文档做语义理解后提供搜索能力,返回的是"最相关的文档片段",不像 Knowledge Bases 那样把检索结果喂给大模型生成一段综合性回答。它更像"更聪明的企业内部搜索框",不是一个 RAG 组件。

**案例**:一家企业想给员工做内部搜索工具,能理解"报销流程"和"费用报销怎么走"是同一个意思,用 Kendra 搭建搜索入口,员工搜索后直接看到最相关的几份内部文档链接,不需要模型生成综合性回答。

### ★★☆ Amazon Q Business
**开箱即用的企业知识助手**

Amazon Q Business 是一个不用写代码的成品级企业问答应用,接入企业的各类数据源后,员工可以直接用自然语言提问、得到综合性回答,背后已经把 RAG 检索、生成这些环节封装好了。跟自己用 Knowledge Bases + Bedrock 搭一套 RAG 系统相比,Q Business 省去大量开发工作,但定制化程度和灵活度也相应更低。

**案例**:一家中型企业想快速给员工上线一个"能问公司政策"的智能助手,又没有太多工程师资源自己搭建,直接采购 Amazon Q Business,接入内部文档几天内就能用起来。

### ★★☆ SageMaker JumpStart
**一键部署开源模型到自己的端点**

SageMaker JumpStart 提供一个开源模型库,可以一键把里面的开源模型部署成一个专属于你自己的推理端点,不用自己从零搭建模型部署的基础设施。这跟 Bedrock 调用别人已经托管好的模型不同,JumpStart 部署出来的是"你自己独占的一个端点"。

**案例**:一个团队想用一个特定的开源图像分类模型,又不想自己搭建 GPU 服务器和推理服务,用 JumpStart 几步就能把这个模型部署成一个可以直接调用的 API 端点。

### ★★☆ SageMaker Model Monitor / Clarify / Model Registry
**传统机器学习模型的监控、可解释性与版本管理三件套**

这三个工具服务于"自己训练/部署传统机器学习模型"这条线,跟生成式 AI 关系不大,但考纲提到过要能区分:**Model Monitor** 持续监控生产环境里模型表现是否出现"漂移"(输入数据分布和训练时不一样了,导致效果下降);**Clarify** 检测模型是否存在偏差、帮助解释模型为什么做出某个判断;**Model Registry** 管理不同版本的模型,记录每个版本的效果和血缘关系。

**案例**:一家银行用传统机器学习模型做贷款审批打分,用 Model Monitor 持续盯着这个模型的输入数据有没有随时间明显变化,一旦发现漂移就触发重新训练流程。

### ★★☆ Augmented AI(A2I)
**人工审核回环**

A2I 让你在自动化流程里插入一个"低置信度结果转人工审核"的环节——比如 Textract 提取表单时,某个字段的识别置信度低于阈值,A2I 自动把这份文档转给人工审核,确认或修正后再继续走后面流程,而不是让不确定的自动化结果直接流入下游造成错误。

**案例**:一家企业用 Textract 自动处理身份证识别,遇到手写字迹模糊、置信度低于 90% 的情况,A2I 自动把这张图片转给人工审核员复核,而不是让系统直接采信一个可能识别错的结果。

### ★★☆ Amazon Lex
**对话机器人框架**

Lex 用来构建对话式界面(聊天机器人、语音机器人),核心概念是"意图(Intent)"和"槽位(Slot)"——先识别用户想干什么(意图),再收集完成这件事需要的具体信息(槽位,比如订机票需要出发地、目的地、日期)。比自己直接调大模型做对话更结构化,更适合流程固定的场景,现在也常和 Bedrock 配合,Lex 做流程骨架、大模型处理更灵活的自然语言理解部分。

**案例**:一家航空公司的订票客服机器人用 Lex 定义"订机票"这个意图,识别出用户想订机票后,依次收集出发地、目的地、日期这几个槽位信息,信息收集齐了再调用后端订票系统。

### ★☆☆ Transcribe / Polly / Rekognition
**语音转文字、文字转语音、图像识别三件套**

三个相对成熟的传统 AI 服务:**Transcribe** 把语音转成文字;**Polly** 把文字转成自然的语音朗读;**Rekognition** 识别图像/视频里的物体、人脸、场景、文字。在 GenAI 应用里,它们经常作为"输入输出的转换层"配合大模型使用。

**案例**:一个智能语音客服系统,用户说话先经过 Transcribe 转成文字,文字问题交给 Bedrock 生成回答,回答内容再经过 Polly 转成语音播放给用户,形成语音进语音出的体验。

### ☆☆☆ SageMaker 训练相关(HyperPod、Processing、Ground Truth、Neo)
**模型训练相关工具(考纲不考,跳过)**

HyperPod(大规模分布式训练集群管理)、Processing(数据预处理/后处理作业)、Ground Truth(人工标注数据服务)、Neo(模型编译优化)——这几个都是服务"从零训练/优化模型"这条线的工具。**AIP-C01 考纲明确说明不考模型训练和高级 ML 技术**,阶段一可以完全跳过。

# 补充:非产品概念(RAG 工程 / 提示工程 / Agent 工程 / 评测与可观测性 / 负责任 AI 与合规)

这部分内容不对应具体打星的 AWS 产品,配套文档里单独归为"模块 C",本周分布在 Day 24、26、27、28、30 这几天,汇总在这里。

## C1. RAG 工程(Day 26)

- **四大评测指标分两组**:上下文召回率+上下文精确率(管检索环节,是一对跷跷板)、答案忠实度+答案相关性(管生成环节)
- **四种故障模式**对应指标:检索不到→召回率低;检索到错的→精确率低;检索到了但没用上→忠实度问题;上下文太长被稀释→可能同时伤忠实度和相关性
- **排查顺序**:先看这次检索到的内容里有没有正确答案,决定往检索环节还是生成环节细查,不要从头到尾整条链路重新试一遍
- 引用溯源不是评测指标,是给忠实度提供一份用户自己能核实的证据链,企业场景基本必备

## C2. 提示工程(散落在 Day 22–27)

- 结构化输出(让模型稳定返回固定格式,比如 JSON)、系统提示 vs 用户提示的职责划分(Day 22 讲过 system 和 messages 分开设计的意义)
- 提示词的版本管理与迭代(对应 Prompt Management 这个产品,见 12.1)
- 提示注入与防御属于安全范畴,已在 Guardrails 那节(Day 27)详细展开

## C3. Agent 工程(Day 28)

- **推理循环(ReAct)**:把 Tool Use 的往返流程反复执行多轮,模型自己判断"够了没,能不能给答案"
- **短期记忆**靠重复传递对话历史(这轮对话内部);**长期记忆**靠外部存储+检索(跨对话)——两套机制解决不同时间尺度的问题
- **MCP**:工具接入的标准化协议,解决"每个框架都要重新适配一遍工具"的重复劳动问题,类比"标准插座"
- **多 Agent 模式**:Supervisor-Worker(主管分派)、Workflow(接力,顺序固定)、Graph(更复杂的接力网络,有分支汇合)、Swarm(无中心自组织)——复杂度和可控性依次降低,灵活度依次升高
- **什么时候不该用 Agent**:流程能被完全枚举、需要严格不出错的准确性、需要极高速度和并发,这三种场景都该用 Step Functions
- Agent 失控三种形式:死循环(设最大轮数上限)、工具滥用、越权(呼应 AgentCore Identity/Policy)

## C4. 评测与可观测性(Day 30 + 前几周)

- 评测集起步 20-50 道题,覆盖典型场景+边界场景+该拒绝的场景,上线后持续补充新失败案例
- LLM-as-a-judge 的两种系统性偏差(偏好更长答案、位置偏差)及对应缓解办法
- LLM 特有可观测性指标(呼应 Day 19):TTFT、token 用量、成本归因、拒答率——这些今天可以理解为 Bedrock Evaluations + Observability 组件共同要跟踪的东西

## C5. 负责任 AI 与合规(Day 30)

- **六个维度**:公平性、可解释性(对应引用溯源)、隐私与安全(对应 Guardrails 的 PII 遮蔽)、稳健性(能扛住提示注入等攻击)、治理(需要评测集+可观测性+Evaluations 这些工具支撑)、透明度(告知用户在和 AI 交互)
- **三方责任划分**:模型生产者(训练数据质量、模型安全测试)、模型提供方(基础设施安全、数据使用承诺、提供 Guardrails 这类工具)、模型消费者(也就是你自己——场景适不适合、有没有做防护、最终结果要负责)
- **欧洲客户合规三问**:数据驻留(关联 Day 23 的跨区域推理配置文件)、GDPR(被遗忘权、最小化收集、数据处理协议)、EU AI Act(按风险分级监管,越高风险需要越多合规文档)——今天讲的评测报告、可观测性记录,在这个语境下不只是工程实践,本身就是合规证据

## 向量库四选一

| 选项 | 定位 | 适合场景 |
|---|---|---|
| **OpenSearch Serverless** | 功能最全、性能最好,但最贵(有最低 OCU 计费门槛) | 需要复杂检索(混合检索、高频实时查询)、预算充足 |
| **Aurora + pgvector** | 寄生在已有 Aurora 账单里,性价比之王 | 团队本来就在用 PostgreSQL/Aurora,数据规模中等 |
| **Neptune Analytics** | 图数据库+向量能力 | GraphRAG 场景,数据本身是复杂关系网络 |
| **S3 Vectors** | 原生向量支持的对象存储,成本最低,查询性能相对较弱(延迟约100ms起) | 数据量极其庞大(十亿级)、查询频率不算特别高、对成本极度敏感 |

## Knowledge Bases vs Kendra vs Amazon Q Business

| | Knowledge Bases | Kendra | Amazon Q Business |
|---|---|---|---|
| 本质 | 托管的 RAG 组件,自己写代码组装 | 企业搜索引擎,返回文档片段 | 开箱即用的成品问答应用 |
| 要不要写代码 | 要 | 要(至少搭个前端调用) | 基本不用 |
| 返回什么 | 检索片段,或生成后的综合回答 | 最相关的文档链接/片段,不生成综合回答 | 直接生成的综合性自然语言回答 |
| 灵活度 | 最高,能自定义分块/检索/生成每一环节 | 中等,主要是搜索能力的定制 | 最低,基本是配置项而非代码定制 |
| 适合场景 | 要自己构建有深度定制需求的 RAG 应用 | 只需要"更聪明的企业内部搜索框" | 想快速上线,没有太多工程资源自己搭 |

## Bedrock Agents vs AgentCore vs Step Functions vs Strands

| | 定位 | 谁来管"推理逻辑" |
|---|---|---|
| **Bedrock Agents** | 托管的单 Agent 产品,交钥匙式 | Bedrock 自己管好整个 ReAct 循环,基本不用自己写 |
| **AgentCore** | Agent 的生产化基础设施(Runtime/Gateway/Memory/Identity等七件套) | 不管推理逻辑,只管"这个 Agent 怎么稳定跑在生产环境" |
| **Strands Agents** | AWS 开源的 Agent 开发框架 | 提供自己写推理逻辑(含多 Agent 协作模式)时用的工具库 |
| **Step Functions** | 确定性工作流编排 | 没有"推理",下一步走哪条分支是设计阶段写死的 |

**关系梳理**:流程能提前枚举清楚→ Step Functions,不需要 Agent。需要 Agent 但想快速交钥匙上线→ Bedrock Agents。需要 Agent 又要自己精细控制推理逻辑→ 用 Strands 这类框架写推理逻辑,再用 AgentCore 承载这个 Agent 的生产化运行(两者是配合关系,不是二选一)。

## Bedrock Evaluations vs SageMaker Clarify vs A2I

| | 评估的是什么 | 适用场景 |
|---|---|---|
| **Bedrock Evaluations** | 生成式模型的输出质量(准不准、忠不忠实、语气对不对) | GenAI 应用的效果评测,对应 Day 30 的三种评测模式 |
| **SageMaker Clarify** | 传统机器学习模型的偏差和可解释性 | 自己训练/部署的传统 ML 模型(比如贷款审批打分模型) |
| **A2I** | 不是"评估",是人工审核回环——低置信度结果转人工处理 | 任何自动化流程里需要"不确定就转人工"这道兜底机制的场景 |

**一句话区分**:Evaluations 管"生成式模型说得好不好",Clarify 管"传统 ML 模型的判断公不公平、能不能解释",A2I 不评估任何东西,它是流程里的一道"拿不准就叫人"的安全阀。
