# 模块一:联网和内容分发(共 8 项)

## 1.1 全部 8 项服务简介

### ★★★ Amazon VPC
**云中的私有网络空间**

AWS VPC(Virtual Private Cloud)让你在 AWS 云中划出一块逻辑上完全隔离的私有网络,你可以自定义 IP 地址范围(CIDR)、划分子网、配置路由表和网关,决定哪些资源能连公网、哪些完全隔离。VPC 是几乎所有 AWS 架构的网络地基——EC2、RDS、Lambda(配置了 VPC 的情况下)等资源都运行在某个 VPC 的某个子网里,你对整个网络拓扑拥有完全的控制权。

**案例**:一家企业把网站前端服务器放在公有子网(能被用户访问),把数据库放在私有子网(不能被外部直接访问),通过 VPC 把这两层隔离开,既保证网站能访问,又保护数据库不暴露在公网上。

### ★★★ Amazon API Gateway
**托管的 API 入口**

API Gateway 是一个全托管服务,用来创建、发布、维护、监控和保护 REST、HTTP、WebSocket 类型的 API,你不需要自己搭服务器处理 API 请求的路由、鉴权、限流、监控这些工作,全部由它代劳。它经常和 Lambda 搭配,组成完全无服务器的后端架构:请求先到 API Gateway,再由它触发对应的 Lambda 函数处理。

**案例**:一个创业团队的移动 App,后端逻辑全部用 Lambda 函数实现,通过 API Gateway 把这些函数暴露成一套标准的 REST API 供 App 调用,不用自己维护任何服务器。

### ★★★ Amazon CloudFront
**AWS 的全球内容分发网络(CDN)**

CloudFront 把你的内容(网页、图片、视频、软件安装包等)缓存到 AWS 遍布全球的边缘节点上,用户访问时会被自动路由到离他们最近的节点,大幅降低访问延迟。源站可以设成 S3、EC2 甚至你自己的服务器,常和 WAF、ACM 搭配,一起组成加速 + 防护 + HTTPS 的前端交付方案。

**案例**:一家电商网站把商品图片存在 S3,前面挂一层 CloudFront,全球用户打开网站时图片都从附近的边缘节点加载,不用每次都跨大洋去源站请求。

### ★★★ AWS Direct Connect
**到 AWS 的专用物理网络连接**

Direct Connect 在你的数据中心和 AWS 之间建立一条专用的物理网络链路,完全不经过公共互联网,能提供比普通网络连接更稳定的带宽和更低的延迟。搭建周期相对较长(涉及物理布线,通常几周到几个月),成本也比 VPN 高,一般是数据量大、对稳定性和合规要求高的企业才会用。

**案例**:一家跨国制造企业每天要把工厂设备产生的大量数据同步到 AWS 做分析,公网 VPN 经常拥堵,改用 Direct Connect 后传输稳定性和速度都大幅提升。

### ★★★ AWS Global Accelerator
**让全球用户就近接入你的应用**

Global Accelerator 利用 AWS 遍布全球的骨干网络(而不是公共互联网),把用户请求路由到离他们最近、健康状况最好的应用端点,还能提供固定的锚点 IP 地址——即使后端资源发生变化,用户访问的入口 IP 也不变。常用于对延迟敏感、面向全球用户、且需要故障自动转移能力的应用。

**案例**:一款全球在线游戏用 Global Accelerator 把不同大洲的玩家路由到最近的区域服务器,某个区域故障时自动切换到健康区域,玩家几乎无感知。

### ★★★ Amazon Route 53
**高可用的域名解析服务**

Route 53 是 AWS 的 DNS 服务,负责把域名解析成 IP 地址,同时支持域名注册和健康检查。最大的亮点是提供七种路由策略(简单、加权、延迟、故障转移、地理位置、地理邻近、多值),可以根据用户所在地、后端健康状态等条件,把流量灵活分发到不同资源。

**案例**:一家公司在美国和欧洲各部署一套系统,用地理邻近路由让美国用户自动解析到美国服务器、欧洲用户解析到欧洲服务器,配合健康检查,某区域故障时自动把流量切到另一区域。

### ★★★ AWS VPN
**通过公网加密连接到 VPC**

AWS VPN 在你的本地网络和 VPC 之间建立一条基于 IPsec 协议的加密隧道,流量走公共互联网,但传输过程全程加密。相比 Direct Connect,VPN 搭建速度快(通常几分钟到几小时能配好)、成本低,但带宽和延迟的稳定性不如专用物理连接。

**案例**:一家中小企业要让员工远程办公时安全访问公司 AWS 内部系统,又不想承担 Direct Connect 的高成本和长周期,选择用 Site-to-Site VPN 快速搭一条加密通道。

### ★★★ AWS Transit Gateway
**多 VPC 互联的中心枢纽**

如果企业有几十上百个 VPC 要互相连通,单纯用 VPC Peering 一对一打通会形成复杂的网状连接,数量呈指数级增长难以管理。Transit Gateway 提供一个中心网关,所有 VPC 和本地网络只需要连接到这一个枢纽,由它统一转发流量,大幅简化互联架构的管理复杂度。

**案例**:一家大型企业有生产、测试、数据分析等几十个 VPC,过去用 Peering 两两连接管理混乱,换成 Transit Gateway 后所有 VPC 只需接入这一个枢纽,新增 VPC 时也只用配一条连接。

## 1.2 本周深化的重点:VPC(Day 1–3)

这 8 项里,本周深挖的只有 **VPC** 这一项,但深挖的其实是 VPC 内部的四块子机制:数据流路径、安全组/NACL、路由表选路、VPC Endpoint。

**① 公有/私有子网的判定与数据流(Day 1)**
- "公有/私有子网"的本质是**路由表里有没有到 IGW 的 0.0.0.0/0 路由**,不是子网自带的属性——删掉这条路由,子网瞬间变私有
- 公有子网出网:IGW 做 **1:1 静态 NAT**,把私有 IP 换成绑定的公网/弹性 IP
- 私有子网出网:靠**NAT 网关**做 **PAT(多对一)转换**,NAT 网关本身必须部署在公有子网(它自己也要靠公有子网的路由才能上网)
- CIDR 计算:/24 理论 256 个地址,AWS 保留 5 个(网络地址、路由器、DNS 保留、AWS 保留、广播地址),实际可用 251 个

**② 安全组、NACL 与路由表选路(Day 2)**
- 安全组(实例层)**有状态**——回程流量自动放行,不用配出站规则
- NACL(子网层)**无状态**——进出流量要分别配规则,是最容易漏配导致连接单向不通的坑
- 安全组**只有允许规则**,没法拒绝某个 IP;要拉黑一个 IP 必须去 NACL 配一条**编号较小**的拒绝规则(按编号从小到大评估,第一条匹配的生效)
- 路由表选路靠**最长前缀匹配**——匹配范围越精确优先级越高,跟规则写的物理顺序无关

**③ VPC Endpoint 与 PrivateLink(Day 3)**
- 默认调用 S3、Bedrock 这类 AWS 自家服务也要走公网(它们对外暴露的是公网地址),得绕经 NAT 网关 + IGW
- **Gateway 型**:只服务 S3 和 DynamoDB,本质是路由表多一条规则,不占实体资源,**免费**
- **Interface 型(PrivateLink)**:支持绝大多数服务含 Bedrock,会在子网里创建一块**真实网络接口(ENI)**,按小时+流量收费
- PrivateLink 只开放一个具体服务(对方看不到你 VPC 里其他任何东西);VPC Peering 是把两个 VPC 整个网段打通,两者定位不同

## 1.3 架构图/流程(文字描述)

**公有子网出网**
```
EC2(公网/弹性IP)→ 子网路由表(0.0.0.0/0→IGW)→ IGW(1:1 NAT)→ 互联网
```

**私有子网出网**
```
EC2(仅私有IP)→ 私有子网路由表(0.0.0.0/0→NAT网关)
→ NAT网关(PAT转换,在公有子网内)→ 公有子网路由表 → IGW → 互联网
```

**外部请求进入 VPC 到达 EC2**
```
外部请求 → IGW(1:1 NAT)→ 路由表(决定送到哪个子网)
→ NACL(子网层,无状态)→ 安全组(实例层,有状态)→ EC2 网卡
```

**私有子网 Lambda 调 Bedrock,全程不出公网**
```
Lambda(私有子网内)→ 私有子网路由表 → Bedrock 的 Interface Endpoint(私有IP)
→ AWS 内部网络直达 Bedrock(不经过 NAT 网关和 IGW)
```

# 模块二:安全性身份和合规规性(共 19 项)

## 2.1 全部 19 项服务简介

### ★☆☆ AWS Artifact
**合规文件自助下载门户**

Artifact 是一个按需自助式门户,里面存放着 AWS 的各类合规报告和协议,比如 SOC 1/2/3 报告、PCI DSS 认证证明、各类国际/行业合规认证文件。企业做安全审计或需要向客户证明"AWS 基础设施本身是合规的"时,直接从这里下载官方文件即可,不需要额外申请。

**案例**:一家金融 SaaS 公司在给客户做安全审计时,需要提供云基础设施供应商的合规证明,直接从 Artifact 下载 SOC 2 报告附在审计材料里。

### ☆☆☆ AWS Audit Manager
**自动化合规证据收集**

Audit Manager 持续自动收集你 AWS 环境里的配置和活动证据,对照某个合规框架(比如 GDPR、HIPAA、PCI-DSS)的要求,自动生成合规评估报告,省去人工挨个截图、整理证据的繁琐工作。

**案例**:一家医疗科技公司要定期做 HIPAA 合规审计,用 Audit Manager 持续跟踪相关配置项是否达标,审计季直接导出现成的证据报告。

### ★★★ Amazon Inspector
**自动化漏洞扫描**

Inspector 自动扫描 EC2 实例和容器镜像,检查已知的软件漏洞(CVE)、意外的网络暴露面等安全隐患,并给出风险评分和修复建议。它可以持续运行,一旦发现新的高危漏洞会主动告警,不用等人工定期手动扫描。

**案例**:一个团队把 Inspector 接入 CI/CD 流水线,每次构建新容器镜像时自动扫描一遍,发现高危漏洞就阻止这个镜像被部署到生产环境。

### ☆☆☆ AWS CloudHSM
**专属硬件级密钥管理**

CloudHSM 为你提供一台专用的、符合 FIPS 140-2 等严格合规标准的硬件安全模块(HSM),让你在硬件层面生成、存储、管理加密密钥,比 KMS 的软件托管密钥有更高的合规和隔离级别,但成本和管理复杂度也更高。

**案例**:一家银行因监管要求密钥必须存放在专用硬件设备里(不能是软件托管的多租户环境),因此选用 CloudHSM 而不是普通的 KMS。

### ★☆☆ Amazon Detective
**安全事件根因分析**

Detective 自动收集 VPC Flow Logs、CloudTrail、GuardDuty 等多个来源的日志数据,构建成可视化的关系图谱,帮助安全团队在发生安全事件后快速梳理"这次攻击是怎么发生的、影响了哪些资源",大幅缩短事后调查的时间。

**案例**:GuardDuty 检测到一个异常登录行为后,安全团队打开 Detective,顺着图谱一路查清这个异常登录之后触碰过哪些资源、做了哪些操作。

### ☆☆☆ AWS Directory Service
**托管的目录服务**

Directory Service 提供托管版的微软 Active Directory(或轻量的 AD 兼容目录),让企业已有的目录体系可以直接延伸到 AWS 上,不用重新为云上资源单独建一套身份管理系统,常用于企业上云过程中希望保留原有 AD 身份体系的场景。

**案例**:一家企业原本用 AD 管理所有员工账号和权限,上云后用 Directory Service 把 AD 延伸到 AWS,员工用同一套账号既能登录本地系统也能访问 AWS 资源。

### ★☆☆ AWS Firewall Manager
**多账号安全策略集中管理**

Firewall Manager 让你在一个地方集中配置和下发 WAF 规则、安全组规则、Shield 防护策略等安全设置,自动应用到组织下的所有账号和资源上,避免每个团队各自为政导致安全策略参差不齐。

**案例**:一个有几十个业务团队、上百个 AWS 账号的大企业,安全团队用 Firewall Manager 统一下发一套 WAF 基础规则到所有账号,新建的资源也自动套用这套规则。

### ★★★ Amazon GuardDuty
**智能威胁检测**

GuardDuty 是一个托管的威胁检测服务,持续分析 CloudTrail 管理事件、VPC Flow Logs、DNS 查询日志等多种数据源,用机器学习和威胁情报识别异常行为(比如异常的 API 调用模式、和已知恶意 IP 的通信),不需要你自己搭建和维护复杂的日志分析系统。

**案例**:GuardDuty 发现某个 EC2 实例突然开始和已知恶意 IP 大量通信,判断可能已被攻破,自动生成一条高危告警,安全团队第一时间介入排查。

### ★★★ AWS Shield
**DDoS 防护**

Shield 保护应用免受分布式拒绝服务(DDoS)攻击。Standard 版本免费,自动为所有 AWS 客户提供基础防护;Advanced 版本收费,提供更高级的检测能力、实时攻击可视化,以及一支专门的响应团队在大规模攻击时协助处置。

**案例**:一个面向公网的电商网站在促销期间遭遇大规模 DDoS 攻击,Shield Advanced 自动识别并缓解了攻击流量,网站没有出现明显的服务中断。

### ★★☆ AWS IAM Identity Center(原 AWS Single Sign-On)
**企业级单点登录**

IAM Identity Center 让员工用同一套身份就能登录访问多个 AWS 账号,也能扩展到第三方 SaaS 应用的登录。它可以对接企业已有的身份提供商(比如 Azure AD),把权限管理和登录入口统一收敛到一个地方,尤其适合有多个 AWS 账号的大型组织。

**案例**:一家有 10 个不同业务线 AWS 账号的公司,过去员工要分别记住 10 套登录凭证,上线 IAM Identity Center 后员工只需登录一次,就能看到自己有权限访问的所有账号。

### ★★★ AWS KMS
**密钥管理服务**

KMS 负责创建和管理用于加密数据的密钥,几乎所有 AWS 服务的静态数据加密功能(S3、EBS、RDS 等)背后都是靠 KMS 提供密钥支持。它采用信封加密的思路:用主密钥加密一个数据密钥,再用数据密钥加密实际数据,主密钥可以是 AWS 托管的,也可以是你自己创建管理的客户管理密钥(拥有更多策略控制权)。

**案例**:一家公司要求 S3 里所有客户数据都必须加密存储,并且要能控制谁有权限使用解密密钥,于是用 KMS 创建一个客户管理密钥,给这个桶配置加密并精细控制密钥使用策略。

### ★☆☆ AWS Certificate Manager(ACM)
**免费的 SSL/TLS 证书管理**

ACM 可以免费签发和自动续期 SSL/TLS 证书,用于给 CloudFront、Application Load Balancer 等服务配置 HTTPS。传统上申请和手动续期证书是件挺麻烦的运维工作,ACM 把这个过程完全自动化,证书到期前会自动续订,不需要人工干预。

**案例**:一个网站上线时用 ACM 免费申请了一张证书挂在 CloudFront 前面,证书到期前自动完成续期,团队完全不用操心证书过期导致网站报 HTTPS 错误的问题。

### ★☆☆ Amazon Macie
**敏感数据自动发现**

Macie 用机器学习技术自动扫描 S3 存储桶,识别和分类里面的敏感数据,比如个人身份信息(PII)、信用卡号、密钥凭证等,并给出这些数据的暴露风险评分,帮助企业在数据合规上少踩坑。

**案例**:一家公司不确定自己 S3 里到底存了多少敏感客户数据、有没有被错误设成公开访问,用 Macie 跑一遍全量扫描,发现并修复了几个意外公开的存储桶。

### ☆☆☆ AWS Resource Access Manager(RAM)
**跨账号资源共享**

RAM 让你可以把某些 AWS 资源(比如子网、Transit Gateway、许可证)安全地共享给组织内的其他 AWS 账号使用,不需要在每个账号里重复创建一份,既省资源又方便统一管理。

**案例**:一家企业有一个专门管网络的账号,建好 Transit Gateway 之后,通过 RAM 把这个网关共享给其他十几个业务账号,业务账号直接接入使用,不用各自重新搭建网络基础设施。

### ★★★ AWS Secrets Manager
**密钥凭证的存储与自动轮换**

Secrets Manager 专门用来存储数据库密码、API 密钥这类敏感凭证,并且支持配置自动定期轮换,轮换时还能自动同步更新到相关的数据库或服务里,不需要人工手动改密码、改配置。应用代码里也就不用硬编码任何密码,全部在运行时向 Secrets Manager 动态获取。

**案例**:一个应用连接的 RDS 数据库密码每 90 天自动轮换一次,Secrets Manager 在轮换的同时自动更新 RDS 的密码配置,应用每次连接前实时从 Secrets Manager 拿最新密码,全程不需要人工介入。

### ★☆☆ AWS Security Hub
**安全态势统一仪表盘**

Security Hub 把 GuardDuty、Inspector、Macie 等多个安全服务的检测结果汇总到一个统一的仪表盘,并对照一些行业安全标准(比如 CIS 基准)给出整体的安全评分和待处理清单,让安全团队不用在好几个服务的控制台之间来回切换。

**案例**:安全团队每天早上打开 Security Hub 的仪表盘,一眼看到昨晚新增的所有高危告警(不管来自 GuardDuty 还是 Inspector),按优先级逐个处理。

### ★★★ AWS WAF
**Web 应用防火墙**

WAF 基于你配置的规则(比如拦截 SQL 注入、跨站脚本攻击、限制单 IP 请求速率)来过滤进入 Web 应用或 API 的 HTTP/HTTPS 流量,通常挂在 CloudFront、ALB 或 API Gateway 前面,拦截恶意流量,保护后端应用不受常见 Web 攻击影响。

**案例**:一个 API 接口被发现频繁遭遇暴力破解攻击,团队在 API Gateway 前配置 WAF 的速率限制规则,同一个 IP 短时间内请求次数超过阈值就自动拦截。

## 2.2 本周深化的重点:IAM(Day 4–5)

**① IAM 策略评估逻辑(Day 4)**
- 五类策略共同决定"有效权限":身份策略、资源策略、SCP、权限边界、会话策略
- 身份策略贴在"人/角色"身上(我能干什么),资源策略贴在"资源"身上(谁能碰我),按**身份维度**判断,不是按 IP——这也是为什么 EC2 没有资源策略能力
- SCP 和权限边界**只做减法**——跟身份策略做交集,只会让权限变少
- **显式 Deny 一票否决**:任何一处明确写"拒绝",不管别处多少个"允许",结果都是不行
- **显式拒绝 vs 隐式拒绝**:前者是白纸黑字写了"不行";后者是操作压根没被任何策略交集覆盖到——效果一样,排查方向相反
- 跨账号访问 S3 为什么两边都要配:同账号只靠身份策略一头够,跨账号必须身份策略和资源策略两边都点头

**② 角色、STS 与凭证(Day 5)**
- IAM User 是长期身份,IAM Role 是可临时借用的身份模板,STS 负责发放临时凭证
- 角色贴两张纸:**信任策略**(谁能借)+ **权限策略**(借完能干啥)
- AssumeRole 流程:发起请求 → STS 查信任策略 → 通过则签发临时三件套(15分钟~12小时)→ 用凭证以角色身份干活 → 到期作废
- **ExternalId**:跨账号场景(如 SaaS 服务商代表多客户操作)防止角色 ARN 被搞混、张冠李戴
- **EC2** 靠实例配置文件 + IMDS,SDK 按需缓存、快过期自动刷新——是"问出来的"
- **Lambda** 靠执行角色,Lambda 服务执行前代为 AssumeRole,凭证注入环境变量——是"塞进去的"
- 生产环境不用长期 Access Key:泄露风险窗口从"可能几个月没发现"压缩到"最多几小时自动失效",且每次 AssumeRole 都有 CloudTrail 审计

## 2.3 本周深化的重点:Cognito(Day 6)

> 星级说明:课程给 Cognito 打的是 ★☆☆(CCP 考试里的边缘条目),阶段一计划把它提到了 ★★★——评价维度变了,CCP 不太考细节,但 AI 工程师做 GenAI 应用加登录时它是标配

- **User Pool**:管认证("你是谁"),认证通过发 JWT
- **Identity Pool**:管授权换证("你能拿到什么 AWS 权限"),拿 JWT 去 STS 换 AWS 临时凭证(本质是 `AssumeRoleWithWebIdentity`,和 Day 5 的 AssumeRole 同一套底层机制)
- 只需纯认证用 User Pool 就够;需要前端直接摸 AWS 资源(浏览器直传 S3、直调 Bedrock)才需要搭上 Identity Pool
- JWT 三件套:**ID Token**(用户属性,证明"你是谁")、**Access Token**(权限范围,给 API 判断能否放行)、**Refresh Token**(换新令牌不用重新登录)
- API Gateway 三种授权:**Cognito Authorizer**(标准场景最省心)、**Lambda Authorizer**(自定义身份系统/复杂逻辑)、**IAM 授权**(调用方本身已是 AWS 身份)
- 关键认知:用户身份通常在到达后端那一刻就"下车"——Lambda 调 Bedrock 用的是**自己的执行角色**,不是用户身份;要做按用户审计得手动解析 JWT
- 社交登录本质是把第三方接成 User Pool 的联合身份提供商,最终收敛成统一格式的 JWT

## 2.4 架构图/流程(文字描述)

**IAM 有效权限判定公式**
```
有效权限 = (身份策略 ∪ 资源策略) ∩ SCP ∩ 权限边界 ∩ 会话策略
且任意一处出现【显式 Deny】,直接一票否决
```

**AssumeRole 借用角色完整流程**
```
发起 AssumeRole 请求 → STS 查角色的信任策略(有没有资格借)
→ 通过则签发临时三件套 → 用凭证以角色身份干活 → 到期作废,需重新借
```

**Web 应用登录 → 调用受保护 API → 后端调 Bedrock**
```
用户登录 → User Pool 认证通过,发 JWT
→ 前端调 API Gateway(带 Access Token)→ Cognito Authorizer 验证令牌
→ 验证通过转发给 Lambda → Lambda 用自己的执行角色(不是用户身份)调 Bedrock
```

**前端跳过后端直调 Bedrock 的分支**
```
User Pool 发的 JWT → 交给 Identity Pool → 调 STS 的 AssumeRoleWithWebIdentity
→ 换到 AWS 临时凭证 → 前端直接拿这套凭证调 Bedrock
```
