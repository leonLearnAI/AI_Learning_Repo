# VPC Peering Cross-VPC Communication Lab Notes

> Region: eu-west-1

---

## 1. Lab Objective

This lab verifies that cross-VPC communication requires **four independent conditions to be satisfied simultaneously** — none of them optional:

- CIDR blocks don't overlap
- The peering connection is in the Active state
- Route tables on both sides point to the peer's CIDR
- Security groups on both sides allow traffic from the peer's CIDR range

It also clarifies two commonly confused concepts:
- Security group "reference by SG ID" vs. "reference by CIDR block" — the former only works **within the same VPC**; across VPCs you must switch to CIDR
- Peering's "DNS resolution" setting only affects **accessing the peer instance by hostname** — pure IP-to-IP access is entirely unaffected by this switch

## 2. Architecture Overview

```text
        VPC-01 (10.0.0.0/16)                       VPC-02 (192.168.0.0/16)
   ┌───────────────────────────┐             ┌───────────────────────────┐
   │                           │             │                           │
   │    ┌─────────────┐        │             │        ┌─────────────┐    │
   │    │   EC2-01     │        │             │        │   EC2-02     │    │
   │    └──────┬──────┘        │             │        └──────┬──────┘    │
   │           │                │             │               │           │
   │    Route table rtb-01      │             │      Route table rtb-02   │
   │    192.168.0.0/16          │◄── Peering ──►│    10.0.0.0/16          │
   │      → pcx-xxx             │  Connection  │      → pcx-xxx           │
   │                           │  (pcx-xxx,   │                           │
   │    Security group: allows │   Active)    │    Security group: allows │
   │    traffic from            │             │    traffic from            │
   │    192.168.0.0/16          │             │    10.0.0.0/16             │
   └───────────────────────────┘             └───────────────────────────┘
```

**The four conditions required for cross-VPC communication**
```text
① CIDR blocks don't overlap
② The peering connection is in the Active state
③ Route tables on both sides point to the peer's CIDR, next hop pcx-xxx
④ Security groups on both sides allow traffic from the peer's CIDR range

Any single condition missing → no connectivity
All four satisfied → cross-VPC communication succeeds
```

**How private-subnet instances are accessed (supplementary architecture)**
```text
A private-subnet EC2 instance has no public IP/DNS by design —
this is expected, not a fault
  │
  ▼
Access it via an EC2 Instance Connect Endpoint instead
(the endpoint and the instance are in the same VPC, so their
 security groups can reference each other by SG ID)
  │
  ▼
Note: even if the endpoint and the instance share the exact
      same security group, that doesn't automatically grant
      mutual access — you still need to explicitly add an
      inbound rule that allows traffic from that same
      security group (a self-reference)
```

**Security group referencing: same VPC vs. cross-VPC**
```text
              Security group reference rules
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
   Within the same VPC          Across VPCs (including peering)
        │                        │
Can directly reference the       Can only reference a
peer's security group ID         CIDR block
(sg-xxx)                         (cross-VPC SG ID reference
                                   is not supported)
```

**One-line conclusion**
```text
A Peering connection being Active only means "the channel exists"
Where traffic actually goes still has to be pointed to manually
via route tables
Security groups decide "is it allowed through" — cross-VPC
scenarios must use CIDR, not SG references
All four conditions are required, none optional
```

## 4. Lab Steps (General Procedure)

- **Step 1: Create two VPCs with non-overlapping CIDRs, each with its own subnet, an attached IGW, and one EC2 instance**
- **Step 2 (if the instance is in a private subnet): Create an EC2 Instance Connect Endpoint for access, and add an inbound rule allowing traffic "from the security group itself"**
- **Step 3: Create the VPC Peering connection, confirm its state is Active**
- **Step 4: Add a route to both route tables pointing to the peer's CIDR, with next hop pcx-xxx**
- **Step 5: Add inbound rules to both security groups allowing the required protocol/port from the peer's CIDR range (cross-VPC scenarios must use CIDR — you cannot reference the peer's security group ID)**
- **Step 6: Run a connectivity test in both directions (e.g., ping the peer's private IP), confirming cross-VPC communication succeeds**

## 5. Key Issues Encountered

### Issue 1: The security group needed an additional "self-reference" rule before the endpoint would connect

**Symptom**: After the EC2 Instance Connect Endpoint was created and showed as available, it still couldn't reach the target instance
**Cause**: The endpoint and the target instance used the **exact same security group** — but sharing a security group doesn't automatically grant mutual access. The connection request from the endpoint still originates from that same security group, so an explicit inbound rule was needed allowing traffic from that security group itself (Type: All traffic, Source: the SG's own ID)
**Resolution**: Added this self-reference rule to the security group's inbound rules — the connection then succeeded
**Takeaway**: Even when two resources share the exact same security group, that doesn't imply mutual access by default — an explicit rule is still required. This rule is fundamentally the same mechanism as "referencing another security group as the Source" — the referenced group just happens to be itself

---

### Issue 2: Mistakenly assumed the ping failure needed to be fixed via Peering's DNS resolution settings (a wrong-direction detour)

**Symptom**: The peering connection was already Active, but the two instances couldn't ping each other over private IPs — an attempt was made to go to the peering connection's "Edit DNS Settings" page and enable "Allow the peer VPC to resolve my private DNS"
**Cause**: This was a directional misunderstanding — the DNS resolution setting only affects accessing the peer instance **by hostname**. Pinging over a **private IP** never touches DNS resolution at all, and is entirely unaffected by this switch
**Resolution**: Abandoned this line of investigation and moved to the more relevant areas — route tables and security groups
**Takeaway**: When facing a connectivity issue, first pin down whether the access in question is by IP or by hostname, then decide whether DNS-level troubleshooting is even relevant — this avoids wasting time on an unrelated setting

---

### Issue 3: A route table CIDR misconfiguration was the reason all four connectivity conditions weren't met (the core issue)

**Symptom**: While checking the four connectivity conditions one by one (peering state, route tables, security groups, CIDR overlap), comparing the two route tables side by side surfaced the problem
**Cause**: The route in `vpc02-route` had its destination written as `0.0.0.0/16` instead of the intended `10.0.0.0/16` — `0.0.0.0/16` only covers a tiny sliver of address space and doesn't include vpc-01's actual CIDR at all, so traffic from vpc-02 destined for vpc-01 never took this peering route — this was the direct cause of the ping failure
**Resolution**: Corrected the route's destination to `10.0.0.0/16`; also added an inbound rule to each side's security group allowing ICMP traffic from the peer's CIDR (vpc-01's EC2 allowed traffic from `192.168.0.0/16`, vpc-02's EC2 allowed traffic from `10.0.0.0/16`) — note this had to use CIDR, not a security group ID reference like in Issue 1, since cross-VPC scenarios don't support SG ID references
**Takeaway**: CIDR values are easy to mistype, and this class of error produces no error message at all — the only way to catch it is to compare route table entries line by line. Security group rules also work completely differently within the same VPC vs. across VPCs, and it's easy to carry over the previous step's approach into the next one by mistake

## 6. Conclusions and Takeaways

1. **Core conclusion**: Cross-VPC communication requires non-overlapping CIDRs, an Active peering connection, correctly configured route tables on both sides, and security groups allowing traffic on both sides — all four conditions simultaneously. Missing any one of them breaks connectivity.
2. **Troubleshooting methodology**: When diagnosing a connectivity issue, work through the "four connectivity conditions" one at a time, rather than intuitively jumping to whatever setting seems most related (in this case, jumping straight to DNS resolution turned out to be a detour).
3. **Security group referencing rules**: "Reference by SG ID" and "reference by CIDR block" have completely different scopes of applicability (the former only within a single VPC, the latter required across VPCs) — it's easy to carry the previous configuration approach into the next step by mistake. Even sharing the same security group doesn't grant mutual access automatically — a self-reference rule still needs to be added explicitly.
4. **An easily overlooked detail**: A mistyped CIDR in a route table (`0.0.0.0/16` vs. `10.0.0.0/16`) produces no system error whatsoever — it can only be caught by manually comparing entries one by one. This class of "looks configured, but configured wrong" issue tends to be the most well-hidden.
