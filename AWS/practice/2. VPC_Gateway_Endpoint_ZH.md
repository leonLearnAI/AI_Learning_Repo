# VPC Gateway Endpoint 访问 S3 实验记录

> Region:eu-west-1 | 课程对应:Kevin LYU Udemy 课程 · 网络篇 VPC Endpoint

---

## 一、实验目标

验证一个核心结论:**IAM 权限**和**网络路径**是两套完全独立的机制,访问 S3 需要两者同时满足。

- IAM 角色 = "有没有权限"(钥匙)
- 网络路由 = "包能不能到达"(路)
- Gateway Endpoint = 给私有子网到 S3 修一条不出 AWS 内部网络的专线路由,**免费**,本质只是路由表里多一条规则

---

## 二、架构总览

```text
                            VPC(10.0.0.0/16)
   ┌────────────────────────────────────────────────────────────────┐
   │                                                                  │
   │   公有子网(pub-sub)                      私有子网(pri-sub)          │
   │  ┌───────────────┐                    ┌───────────────┐          │
   │  │   pub-ec2       │                    │   pri-ec2       │          │
   │  │  + 弹性 IP       │                    │  无公网 IP       │          │
   │  │  + IAM 角色      │                    │  + IAM 角色      │          │
   │  │ (AmazonS3Full-  │                    │ (AmazonS3Full-  │          │
   │  │  Access)        │                    │  Access)        │          │
   │  └────────┬────────┘                    └────────┬────────┘          │
   │           │                                       │                   │
   │   路由表:0.0.0.0/0                          路由表:仅 local            │
   │        → IGW                                       │                   │
   │           │                              ┌─────────┴─────────┐         │
   │           │                              │  Gateway Endpoint   │         │
   │           │                              │  (vpce-xxx)         │         │
   │           │                              │  路由表自动新增:      │         │
   │           │                              │  S3 prefix list      │         │
   │           │                              │   → vpce-xxx         │         │
   │           │                              └─────────┬─────────┘         │
   └───────────┼────────────────────────────────────────┼───────────────────┘
               │                                        │
               ▼                                        ▼
        ┌─────────────┐                        ┌─────────────────┐
        │ IGW → 公网    │                        │  AWS 内部网络       │
        │ → S3(公网路径)│                        │  → S3(私有路径,    │
        └─────────────┘                        │   不出公网)         │
                                                └─────────────────┘
```

**核心结构**
```text
IAM 权限层(角色是否挂载、是否有 S3 权限)
        与
网络路径层(路由表能不能把请求送到 S3)
是两套独立机制,访问 S3 必须两者都满足
```

### 2.1 核心概念图

```text
                    一次 S3 请求
                        │
                 ┌──────┴──────┐
                 │             │
                 ▼             ▼
             IAM 权限层      网络路径层
                 │             │
          "我有没有权限?"   "包能不能到达?"
                 │             │
                 ▼             ▼
               权限            路由
                 │             │
                 └──────┬──────┘
                        ▼
                  成功访问 S3


              Gateway Endpoint
                     │
                     ▼
               提供的是一条"路由"
                     │
                     ▼
        私有子网 EC2 ──────────→ S3
             │
             ├─ 不需要 NAT 网关
             ├─ 不需要公网 IP
             ├─ 不经过公共互联网
             ├─ 全程走 AWS 内部网络
             └─ Gateway Endpoint 本身完全免费
```

**一句话结论**
```text
IAM 决定"能不能访问"
网络路由决定"到不到得了"
Gateway Endpoint 给私有子网的 EC2 一条到 S3 的专用路由
```

## 四、实验步骤(通用流程)

- **步骤 1:创建 VPC、公/私子网、IGW,配置路由表(私有子网故意不配 NAT 网关,便于对比实验效果)**
- **步骤 2:私有子网创建 EC2 Instance Connect Endpoint 用于接入测试**
- **步骤 3:分别启动公有/私有 EC2;创建 IAM 角色(受信任实体为 EC2,挂载 `AmazonS3FullAccess`),分别附加到两台实例**
- **步骤 4(Before 测试):私有 EC2 执行 `aws s3 ls`,验证"IAM 有权限但网络无法到达"这一现象(命令卡住/超时)**
- **步骤 5:创建 S3 Gateway Endpoint——服务类别选 AWS 服务,搜索 `com.amazonaws.<region>.s3`,类型务必选 Gateway(不是 Interface),关联私有子网的路由表**
- **步骤 6(After 测试):私有 EC2 重新执行 `aws s3 ls`,验证秒回成功;检查路由表确认新增了 S3 prefix list → vpce-xxx 这条路由**

## 五、遇到的关键问题

按实际发生顺序记录,共 3 个关键问题。

### 问题 1:把 EC2 Instance Connect Endpoint 误当成 S3 Gateway Endpoint(本次最大的坑)

**现象**:自认为已经完成"创建 Gateway Endpoint"这一步,但 After 测试一直卡住,和 Before 测试没有区别
**原因**:检查私有子网关联的路由表,没有 `pl-xxx → vpce-xxx` 这条路由;回头检查之前建的"端点",发现 ID 前缀是 `eice-`,类型是 **EC2 Instance Connect Endpoint**,而不是 `vpce-` 开头的 **VPC Gateway Endpoint**——这个端点实际上是更早为了 SSH 连接私有 EC2 建的连接端点,跟 S3 完全无关,只是命名(`end-point-s3`)造成了误导。两者创建入口也不同:EIC Endpoint 在"EC2 Instance Connect 端点"菜单,Gateway Endpoint 在"端点(Endpoints)"菜单
**解决**:回到正确的"端点(Endpoints)"入口,重新创建真正的 S3 Gateway Endpoint,并正确关联私有子网路由表
**收获**:资源命名要精确反映真实类型,不能只看名字断定功能;两种 Endpoint 服务的是完全不同的目的(连接管理 vs 私有路由),名字相似但本质不同,遇到"明明建了却不生效"时,第一反应应该是回去核实资源的真实类型

---

### 问题 2:一度以为要创建 IAM 用户而不是角色

**现象**:准备在 pri-ec2 上执行 `aws configure`,打算手动填 Access Key
**原因**:澄清 IAM 用户和 IAM 角色的本质区别——用户对应长期静态密钥,需要手动管理和轮换;角色对应临时凭证,由元数据服务自动下发和轮换,跟着实例生命周期走
**解决**:中断 `aws configure`,改为创建 IAM 角色并挂载到 EC2,不引入任何静态密钥
**收获**:EC2 访问 AWS 服务的标准做法是挂 IAM 角色,不是配置用户密钥;这也是"为什么生产环境不该用长期 Access Key"这条原则的实操印证

---

### 问题 3:角色验证通过后,`aws s3 ls` 依然卡住(验证方式本身有误)

**现象**:环境重建后,用 curl 查询元数据确认角色已生效,但 `aws s3 ls` 还是没反应
**原因**:意识到"查元数据"和"`aws s3 ls`"是两类完全不同性质的调用——前者是本地链路(169.254.169.254),不经过 VPC 路由,只能证明角色挂载成功;后者角色验证通过后还要真正发起一次网络请求到 S3 端点,这一步依然要走私有子网的路由表。而这次重建的环境里,Gateway Endpoint 还没有重新创建
**解决**:回到步骤 5,重新创建 S3 Gateway Endpoint 并正确关联私有子网路由表,问题解决,`aws s3 ls` 秒回并成功列出 `leon-s3-new`
**收获**:验证 IAM 角色是否生效,不能用会触发网络请求的命令(如 `aws sts get-caller-identity`、`aws s3 ls`)作为唯一依据,应该用纯本地的元数据查询单独验证;角色对不对和网络通不通,永远是两条要分开验证的独立链路,这也是本次实验反复印证的核心结论

---

## 六、结论与心得

1. **核心结论**:`IAM 权限 + 网络路由` 是访问 AWS 服务的两个独立必要条件,任何一个不满足都会导致失败,而且两者的报错现象完全不同(权限问题是快速拒绝,网络问题是卡住超时)。
2. **诊断方法论**:排查连通性问题时,选用跟目标协议匹配的工具(HTTPS 用 curl,不用 ping);排查权限问题时,选用不触发网络请求的本地元数据查询(需注意新版本 EC2 默认要求 IMDSv2,查询前需先换取 token),避免把权限层和网络层两类问题混在一起判断。
3. **最大的教训**:AWS 控制台里同名或相似功能的资源入口容易混淆(EC2 Instance Connect Endpoint vs VPC Gateway Endpoint),资源命名要精确反映真实类型,遇到"明明建了却不生效"时,第一反应是回去核实资源的真实类型而不是继续排查下游。

## 七、关键命令速查

```bash
# 元数据查询(IMDSv2)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/

# 网络连通性测试(替代 ping,因为 S3 走 HTTPS 不是 ICMP)
curl -v --max-time 5 https://s3.<region>.amazonaws.com

# S3 验证
aws s3 ls
aws s3 cp test.txt s3://<桶名>/
```
