# CloudFront + S3 OAC 内容分发实验记录

> Region:eu-west-1 | 课程对应:Kevin LYU Udemy 课程 · 网络篇 CloudFront/CDN

---

## 一、实验目标

验证一个容易被望文生义的结论:**CloudFront("CDN")的核心价值不只是内容分发/加速,更关键的是它能在"源站保持公网可达"的前提下,让"只有 CloudFront 自己能读源站"成为可能**。

- 网络可达性 = S3 从创建起就有公网 REST 端点,这一点从未改变
- 权限私有 = S3 默认 Block Public Access,拒绝匿名直连
- OAC(Origin Access Control) = 给 CloudFront 一把"专属钥匙",让它代表用户去读私有的 S3

核心对比实验:同一个对象,**直连 S3 URL(AccessDenied)** vs **经 CloudFront 域名访问(成功)**——这组前后对比证明的不是"打通了网络",而是"收紧了权限、同时保留了公网入口"。

## 二、架构总览

```text
                    Internet / 用户
                          │
                          ▼
              ┌─────────────────────────┐
              │        CloudFront          │
              │      (边缘节点分配)          │
              │                           │
              │   Origin Access Control    │
              │   (OAC) = CloudFront       │
              │   专属身份                  │
              └────────────┬──────────────┘
                           │ 用 OAC 身份对请求做 SigV4 签名
                           ▼
              ┌─────────────────────────┐
              │          S3 源站            │
              │                           │
              │   Block Public Access      │
              │   默认开启(拒绝匿名直连)     │
              │                           │
              │   Bucket Policy:           │
              │   只信任这一个 CloudFront    │
              │   distribution 的 OAC 身份  │
              └─────────────────────────┘
```

**两条访问路径对比**
```text
用户 → S3 直连 URL       → 403 AccessDenied(权限层拒绝,网络路径本身通畅)
用户 → CloudFront 域名   → OAC 签名 → S3 验证通过 → 200 成功
```

### 2.1 核心概念图

```text
【OAC 工作原理】

  用户请求
     │
     ▼
CloudFront 边缘节点
     │
   缓存未命中?
     │ 是
     ▼
CloudFront 用 OAC 身份
对请求做 SigV4 签名
     │
     ▼
   S3 验证签名
     │
   只认这一个 distribution 的身份
     │
     ▼
   返回内容 ✅
   (普通匿名请求在这一步就会被拒绝)


【CloudFront 的能力分层——不只是"分发"】

              CloudFront
         (源站前的可编程网关)
                 │
   ┌──────┬──────┼──────┬──────┐
   ▼      ▼      ▼      ▼      ▼
 缓存   安全   访问   TLS    边缘
 加速   防护   控制   卸载   计算
   │      │      │      │      │
 边缘   Shield  OAC   ACM  Lambda@Edge
 节点   /WAF   签名URL 证书 CF Functions
 就近          地理限制
 返回

 本次实验只触达了①缓存加速(表层)
 和 ③访问控制(OAC)这两层
```

**一句话结论**
```text
S3 的公网可达性从头到尾没变过
变的是"谁被允许读"——这是 OAC 收紧的结果
CloudFront 不等于"内容分发",而是源站前的可编程边缘网关,
分发加速只是它众多能力里最表层的一个
```

## 四、实验步骤(通用流程)

- **步骤 1:确认 S3 源站桶已存在且对象已上传;确认默认状态下直连对象 URL 返回 AccessDenied(Block Public Access 默认开启,属于预期行为)**
- **步骤 2:创建 CloudFront 分配,使用场景选择匹配实际需求(如 Single website or app)**
- **步骤 3:Origin type 选择 Amazon S3,用 Browse S3 选择源站桶(不手动填 URL,避免误选成不支持 OAC 的 S3 网站托管端点)**
- **步骤 4:Settings 选择"Use recommended origin settings",自动创建并绑定 OAC,同时自动更新 S3 bucket policy**
- **步骤 5:安全防护页按需决定是否启用 WAF(单独计费)**
- **步骤 6:创建后等待 Last modified 从 Deploying 变为具体时间戳,确认全球边缘节点部署完成**
- **步骤 7:测试对比——CloudFront 域名访问应成功显示图片,S3 直连 URL 应依然 AccessDenied,验证 OAC 生效**

**创建 CloudFront 分配 — 关键步骤选什么、为什么这么选**

| 步骤 | 选择项 | 为什么这么选 |
|---|---|---|
| 使用场景 | Single website or app | 本次只分发一张静态图片,场景匹配,控制台据此给出精简后的默认配置 |
| Origin type | Amazon S3 | 源站是 S3 桶,不是自定义 HTTP 服务器 |
| S3 origin | 用 **Browse S3** 选中源站桶,不手动填 URL | 手动填容易误填成 S3 网站托管端点格式(`s3-website-` 开头),这种端点类型**不支持 OAC**,会导致后续权限收紧失败 |
| Settings | **Use recommended origin settings** | 自动创建并绑定 OAC,同时自动更新 S3 bucket policy,取代旧版教程里"手动复制粘贴 policy JSON"这一步 |
| 安全防护页 | 不启用 WAF | WAF 是单独计费项,一张图片的学习实验不需要应用层过滤规则 |

## 五、遇到的关键问题

按实际发生顺序记录,共 2 个概念性问题。

### 问题 1:误以为本次实验是把"仅 VPC 可访问"的 S3 内容开放到公网

**现象**:实验完成后描述为"把 S3 中存放的只能用 VPC 网络访问的内容,通过 CDN 分发到了公网 edge"
**原因**:这个前提本身不成立——S3 桶从创建起就有公网可达的 REST 端点,从未被限制在 VPC 内部。关键证据是直连该 URL 时,浏览器收到的是一个格式完整的 `AccessDenied` XML 响应,而不是连接失败或超时——如果网络层真的不通,请求根本到不了 S3 去产生这个响应
**解决**:用"钥匙 vs 路"的框架纠正:这次的限制在"钥匙"(IAM/bucket policy 权限层),不是"路"(网络可达性层),S3 的网络路径全程没有变过
**收获**:"打不开"这个现象背后可能是网络层或权限层两种完全不同的原因,响应内容本身(超时/连接失败 vs 明确的错误响应体)是区分这两层的关键证据

---

### 问题 2:误以为 CDN 的作用只是内容分发/加速

**现象**:提出"CDN 是不是不仅仅是做一个内容分发"的疑问
**原因**:回顾本次实验实际验证的内容——OAC 带来的效果本质是访问控制层面的收紧,而不是分发加速本身
**解决**:明确 CloudFront 的定位是源站前的可编程边缘网关,已知能力至少包含:缓存加速、安全防护(Shield/WAF)、访问控制(OAC/签名 URL/地理限制)、TLS 卸载、边缘计算(Lambda@Edge/CloudFront Functions)五层,本次实验只触达了前两层
**收获**:"CDN"这个中文译名容易让人锚定在"分发"这一个功能上,产品的实际定位要看它在架构图里所处的位置(源站前的统一入口),而不是望文生义

## 六、结论与心得

1. **核心结论**:S3 源站的公网可达性从始至终没有改变,变的是"谁能读"——OAC 让 CloudFront 成为唯一被授权的身份。这是此前 VPC 实验"IAM ≠ 网络"框架的延伸版本:这次验证的是"网络可达 ≠ 权限开放"。
2. **新旧控制台差异**:现行 CloudFront 控制台相比旧版教程做了合并简化,OAC 不再是独立的手动步骤,而是被"Use recommended origin settings"这一个开关自动包含。照着新教程操作时,最好养成"这个自动化开关背后对应哪几步手动操作"的习惯,避免知其然不知其所以然。
3. **诊断方法论**:排查访问失败时,先看响应内容本身而非只看"打不开"——连接超时/DNS 失败指向网络层,明确的错误响应体(如 AccessDenied XML)指向权限层。这个判断顺序值得迁移到以后遇到的类似场景(比如 API Gateway、ALB 访问异常)。
4. **CDN 心智模型**:CDN 的价值需要跳出"内容分发"字面意思,理解为源站前的可编程边缘网关。这个模型在后续接触 WAF、签名 URL、Lambda@Edge 这些内容时会持续复用。

## 七、检查清单

- [ ] S3 桶已创建,Block Public Access 保持默认开启(不要为了"能直接访问"而手动开放公开权限)
- [ ] CloudFront 分配创建时,使用场景选 Single website or app
- [ ] Origin type 选 Amazon S3,用 Browse S3 选桶(不要手动填 URL,避免选成网站托管端点)
- [ ] Settings 选 Use recommended origin settings,自动生成 OAC 并更新 bucket policy
- [ ] 安全防护页跳过 WAF(学习阶段省钱)
- [ ] 创建后等 Last modified 从 Deploying 变为具体时间戳再测试
- [ ] 测试对比:CloudFront 域名可正常访问 vs 直连 S3 URL 依然 AccessDenied
- [ ] (可选)CloudFront 在 Always Free 额度内不产生费用,可保留用于后续验证缓存失效(Invalidation)等概念,也可选择清理保持账户整洁
