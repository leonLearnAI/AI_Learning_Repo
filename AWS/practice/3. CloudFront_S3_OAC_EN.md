# CloudFront + S3 OAC Content Delivery Lab Notes

> Region: eu-west-1 | Course reference: Kevin LYU's Udemy course · Networking module, CloudFront/CDN

---

## 1. Lab Objective

This lab verifies a conclusion that is easy to misread from the name alone: **CloudFront's ("CDN's") core value isn't just content delivery/acceleration — its more critical function is making it possible for "S3 stays publicly reachable" and "only CloudFront itself can read S3" to hold true at the same time**.

- Network reachability = the S3 bucket has had a public REST endpoint since creation, and this never changed
- Access privacy = S3 defaults to Block Public Access, rejecting anonymous direct requests
- OAC (Origin Access Control) = gives CloudFront a dedicated "key" to read the private S3 bucket on the user's behalf

Core comparison test: the same object, accessed via **direct S3 URL (AccessDenied)** vs. **via the CloudFront domain (success)**. This before/after pair doesn't prove "the network got opened up" — it proves "access was tightened while the public entry point was preserved."

                           │ its OAC identity
                           ▼
              ┌─────────────────────────┐
              │        S3 origin            │
              │                           │

              │   enabled by default        │
              │   (rejects anonymous        │
              │   direct requests)          │
              │                           │

              │   trusts only this one      │

              │   OAC identity               │
              └─────────────────────────┘

**Two access paths compared**
```text
Viewer → direct S3 URL      → 403 AccessDenied (rejected at the
                                access layer; the network path
                                itself is fine)
Viewer → CloudFront domain  → OAC signs the request → S3 verifies
                                it → 200 success
```

## 4. Lab Steps (General Procedure)

- **Step 1: Confirm the S3 origin bucket exists and the object is uploaded; confirm that by default, a direct request to the object URL returns AccessDenied (Block Public Access is on by default — this is expected, not an error)**
- **Step 2: Create a CloudFront distribution, choosing a use case that matches the actual need (e.g., Single website or app)**
- **Step 3: Set Origin type to Amazon S3, and select the origin bucket via Browse S3 (don't type the URL manually — avoid accidentally selecting the S3 website-hosting endpoint, which doesn't support OAC)**
- **Step 4: Under Settings, choose "Use recommended origin settings," which auto-creates and attaches OAC while also auto-updating the S3 bucket policy**
- **Step 5: On the security protections page, decide whether to enable WAF as needed (billed separately)**
- **Step 6: After creation, wait for Last modified to change from Deploying to a specific timestamp, confirming global edge deployment is complete**
- **Step 7: Run the before/after comparison — the CloudFront domain should successfully display the image, while the direct S3 URL should still return AccessDenied, confirming OAC is working**

**Creating the CloudFront Distribution — Key Choices and Rationale**

| Step | Choice | Why |
|---|---|---|
| Use case | Single website or app | This lab only delivers a single static image — the use case matches, and the console offers a simplified default config accordingly |
| Origin type | Amazon S3 | The origin is an S3 bucket, not a custom HTTP server |
| S3 origin | Use **Browse S3** to select the origin bucket, don't type the URL manually | Typing it manually risks picking the S3 website-hosting endpoint format (starting with `s3-website-`), which **doesn't support OAC** and would cause the access-tightening step to fail later |
| Settings | **Use recommended origin settings** | Auto-creates and attaches OAC, and auto-updates the S3 bucket policy — replacing the old tutorial's "manually copy-paste the policy JSON" step |
| Security protections page | Don't enable WAF | WAF is billed separately; a single-image learning lab doesn't need application-layer filtering rules |

## 5. Key Issues Encountered

Recorded in the order they actually occurred — 2 conceptual issues total.

### Issue 1: Mistakenly assumed this lab was "bridging VPC-only S3 content to the public internet"

**Symptom**: After completing the lab, the setup was described as "taking S3 content that could only be accessed via VPC network and delivering it to the public edge through CDN"
**Cause**: This premise doesn't hold — the S3 bucket has had a publicly reachable REST endpoint since it was created, and was never restricted to VPC-internal access. The key evidence: when hitting that URL directly, the browser received a complete, well-formed `AccessDenied` XML response — not a connection failure or timeout. If the network layer truly weren't reachable, the request would never have reached S3 to produce that response in the first place
**Resolution**: Corrected using the "key vs. road" framework — this time what was limiting access was the "key" (the IAM/bucket-policy access layer), not the "road" (network reachability); S3's network path never changed throughout
**Takeaway**: A "can't open this" symptom can stem from two entirely different causes — the network layer or the access layer. The response content itself (timeout/connection failure vs. an explicit error response body) is the key evidence for telling them apart

---

### Issue 2: Mistakenly assumed a CDN's role is limited to content delivery/acceleration

**Symptom**: Raised the question "isn't a CDN more than just content delivery?"
**Cause**: Reviewed what this lab actually verified — the effect produced by OAC is fundamentally about tightening access control, not delivery acceleration itself
**Resolution**: Clarified that CloudFront's actual role is a programmable edge gateway in front of the origin, with known capabilities spanning at least five layers: cache acceleration, security protection (Shield/WAF), access control (OAC/signed URLs/geo-restriction), TLS offload, and edge compute (Lambda@Edge/CloudFront Functions). This lab only touched the first two layers
**Takeaway**: The English name "CDN" (and its Chinese translation) tends to anchor people on "delivery" as the single function. A product's actual role is defined by its position in the architecture (a unified entry point in front of the origin), not by a literal reading of its name

## 6. Conclusions and Takeaways

1. **Core conclusion**: The public reachability of the S3 origin never changed from start to finish — what changed is "who is allowed to read it," a result of OAC making CloudFront the sole authorized identity. This extends the "IAM ≠ network" framework from the earlier VPC lab: this time the lesson is "network reachability ≠ open access."
2. **Old vs. new console differences**: The current CloudFront console has consolidated and simplified compared to older tutorials — OAC is no longer a separate manual step, but is now folded into the single "Use recommended origin settings" toggle. When following a newer tutorial, it's worth developing the habit of asking "which manual steps does this automated toggle actually stand in for," to avoid knowing the *what* without the *why*.
3. **Troubleshooting methodology**: When diagnosing an access failure, look at the response content itself rather than just "it doesn't load" — a connection timeout or DNS failure points to the network layer, while an explicit error response body (like the AccessDenied XML) points to the access layer. This diagnostic ordering is worth carrying forward to similar scenarios later on (e.g., API Gateway, ALB access issues).
4. **CDN mental model**: A CDN's value needs to be understood beyond the literal meaning of "content delivery" — as a programmable edge gateway sitting in front of the origin. This model will keep being useful when working with WAF, signed URLs, and Lambda@Edge later on.
