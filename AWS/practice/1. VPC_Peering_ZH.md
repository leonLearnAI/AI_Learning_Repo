# VPC Peering 跨 VPC 通信实验记录

> Region:eu-west-1

---

## 一、实验目标

验证跨 VPC 通信需要**四个独立条件同时满足**,缺一不可:

- CIDR 不重叠
- 对等连接(Peering Connection)处于 Active 状态
- 双向路由表都指向对方 CIDR
- 双向安全组都放行对方 CIDR 段的流量

同时厘清两个容易搞混的概念:
- 安全组"引用安全组 ID" vs "引用 CIDR 段"——前者只能用于**同一 VPC 内**,跨 VPC 必须换成 CIDR
- Peering 的"DNS 解析"设置只影响**用主机名访问对方实例**这个场景,纯 IP 互访完全不受这个开关影响

---

## 二、架构总览

```text
        VPC-01(10.0.0.0/16)                       VPC-02(192.168.0.0/16)
   ┌───────────────────────────┐             ┌───────────────────────────┐
   │                           │             │                           │
   │    ┌─────────────┐        │             │        ┌─────────────┐    │
   │    │   EC2-01     │        │             │        │   EC2-02     │    │
   │    └──────┬──────┘        │             │        └──────┬──────┘    │
   │           │                │             │               │           │
   │    路由表 rtb-01            │             │           路由表 rtb-02    │
   │    192.168.0.0/16          │◄── Peering ──►│    10.0.0.0/16          │
   │      → pcx-xxx             │  Connection  │      → pcx-xxx           │
   │                           │  (pcx-xxx,   │                           │
   │    安全组:放行来自          │   Active)    │    安全组:放行来自          │
   │    192.168.0.0/16 的流量    │             │    10.0.0.0/16 的流量      │
   └───────────────────────────┘             └───────────────────────────┘
```

**跨 VPC 通信需要同时满足的四个条件**
```text
① CIDR 不重叠
② Peering 连接处于 Active 状态
③ 双向路由表都指向对方 CIDR,下一跳为 pcx-xxx
④ 双向安全组都放行来自对方 CIDR 段的流量

四者任一缺失 → 无法连通
四者全部满足 → 跨 VPC 通信成功
```

**私有子网实例的接入方式(补充架构)**
```text
私有子网 EC2 没有公网 IP/DNS,是设计使然,不是故障
  │
  ▼
可通过 EC2 Instance Connect Endpoint 接入
(端点与实例在同一 VPC,安全组之间可以互相引用 SG ID)
  │
  ▼
注意:即使端点和实例共用同一个安全组,也不会自动互相放行,
     还需要在该安全组里显式加一条"允许来自自身安全组"的规则
```

**安全组引用方式:同 VPC vs 跨 VPC**
```text
              安全组引用规则
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
   同一个 VPC 内                跨 VPC(含 Peering)
        │                        │
可以直接引用对方的                只能引用 CIDR 网段
安全组 ID(sg-xxx)                (不支持跨 VPC 引用 SG ID)
```

**一句话结论**
```text
Peering 连接 Active 只代表"通道打通了"
流量怎么走,还要靠路由表手动指定
安全组决定"放不放行",跨 VPC 场景必须用 CIDR 而不是 SG 引用
四者缺一不可
```

## 四、实验步骤(通用流程)

- **步骤 1:创建两个 CIDR 不重叠的 VPC,各自创建子网、挂载 IGW、启动一台 EC2**
- **步骤 2(如实例在私有子网):创建 EC2 Instance Connect Endpoint 用于接入,并在安全组中放行"来自自身安全组"的流量**
- **步骤 3:创建 VPC Peering 连接,确认状态为 Active**
- **步骤 4:在双向路由表中添加指向对方 CIDR、下一跳为 pcx-xxx 的路由**
- **步骤 5:在双向安全组中放行来自对方 CIDR 段所需的协议/端口(跨 VPC 场景必须使用 CIDR,不能引用对方的安全组 ID)**
- **步骤 6:双向执行连通性测试(如 ping 对方私有 IP),验证跨 VPC 通信成功**

## 五、遇到的关键问题

### 问题 1:安全组需要额外放行"自身引用"的流量,端点才能连通

**现象**:EC2 Instance Connect Endpoint 建好、状态可用之后,还是连不上目标实例
**原因**:端点和目标实例用的是**同一个安全组**,但共用同一个安全组不代表默认互相放行——端点发出的连接请求,源仍然是这个安全组本身,需要在这个安全组的入站规则里显式加一条"允许来自自身安全组"的规则(类型:所有流量,源:自身 SG ID)
**解决**:在该安全组入站规则里补上这条自引用规则,重新连接成功
**收获**:即使两个资源共用同一个安全组,也不代表默认互相放行,仍然要显式加规则——这条规则本质上和"引用另一个安全组作为 Source"是同一类机制,只是引用对象恰好是自己

---

### 问题 2:误判 ping 不通需要修复 Peering 的 DNS 解析设置(方向性弯路)

**现象**:Peering 连接已经是 Active 状态,但两台实例用私有 IP 互相 ping 不通,一度尝试去对等连接的"编辑 DNS 设置"页面,勾选"允许对方 VPC 解析本方私有 DNS"
**原因**:这是一个方向性误解——DNS 解析设置只影响"用**主机名**访问对方实例"这个场景,纯用**私有 IP** 执行 ping,根本不经过 DNS 这一步,跟这个开关完全无关
**解决**:放弃这条路线,转向排查路由表和安全组这两个更相关的方向
**收获**:遇到连通性问题,先明确"当前用的是 IP 还是主机名访问",再决定要不要涉及 DNS 层面的排查,避免在无关的设置项上浪费时间

---

### 问题 3:路由表 CIDR 配置错误,导致跨 VPC 连通性四要素未达成(核心问题)

**现象**:排查连通性四要素(Peering 状态、路由表、安全组、CIDR 重叠)时,逐条打开两个路由表比对,发现问题
**原因**:`vpc02-route` 里那条路由的目标写成了 `0.0.0.0/16`,而不是应该的 `10.0.0.0/16`——`0.0.0.0/16` 只覆盖极小一段地址,完全不包含 vpc-01 的真实网段,导致从 vpc-02 发往 vpc-01 的流量根本走不了这条 peering 路由,这是 ping 不通的直接原因
**解决**:把该路由目标修正为 `10.0.0.0/16`;同时在双向安全组各加一条放行对方 CIDR 段流量的规则(vpc-01 的 EC2 放行来自 `192.168.0.0/16`,vpc-02 的 EC2 放行来自 `10.0.0.0/16`)——注意这里必须用 CIDR,不能像问题 1 那样引用对方的安全组 ID,因为跨 VPC 场景不支持安全组 ID 引用
**收获**:CIDR 数值容易手误敲错,而且这类错误不会有任何报错提示,必须逐条比对路由表才能发现;同 VPC 内和跨 VPC 场景下安全组规则的写法完全不同,容易顺着上一次的思路带错

---

## 六、结论与心得

1. **核心结论**:跨 VPC 通信需要 CIDR 不重叠、Peering 连接 Active、双向路由表配置、双向安全组放行这四个条件同时满足,任何一个环节缺失都会导致连不通。
2. **诊断方法论**:排查连通性问题时应该按"连通性四要素"逐项核对,而不是凭直觉先去改看起来最相关的设置(比如先入为主地去改 DNS 解析,结果是条弯路)。
3. **安全组引用规则**:安全组"引用安全组 ID"和"引用 CIDR 段"这两种写法的适用范围完全不同(前者仅限同一个 VPC 内,跨 VPC 必须用 CIDR),很容易把上一步的配置经验直接套用到下一步,造成新的错误;即便共用同一个安全组,也需要显式加自引用规则,不会自动互通。
4. **容易被忽视的细节**:路由表里的 CIDR 数值敲错(`0.0.0.0/16` vs `10.0.0.0/16`)不会有任何系统报错,必须靠逐条人工核对才能发现,这类"看起来配了、但配错了"的问题往往是最隐蔽的。

## 七、下次配置 VPC Peering 检查清单

- [ ] 两个 VPC 的 CIDR 确认不重叠
- [ ] 对等连接状态是否为 Active
- [ ] 两边路由表是否都添加了指向对方 CIDR、target 为 pcx-xxx 的路由(**逐条核对 CIDR 数值是否敲对**)
- [ ] 两边安全组是否都放行了对方 VPC CIDR 段所需的协议/端口(跨 VPC 场景用 CIDR,不能用 SG 引用)
- [ ] 是否真的需要 DNS 解析(只有用主机名访问才需要,用 IP 访问不需要)
- [ ] 实例若在私有子网,是否已准备 EC2 Instance Connect 端点等方式用于测试登录,并确认安全组已放行自引用流量
