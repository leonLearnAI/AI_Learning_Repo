# S3 公共访问实验记录

> Region:eu-west-1 | 课程对应:Kevin LYU Udemy 课程 · 存储篇 S3

---

## 一、实验目标

验证一个容易被混淆的权限概念:**"关闭 Block Public Access" ≠ "已经允许公众读取"**。这是两个独立的开关,分别管两件不同的事——一个决定"公开访问这件事能不能发生"(账户/桶级别的硬性拦截开关),一个决定"具体允许谁、做什么"(Bucket Policy 的实际授权)。两者必须同时满足,对象才能被公网匿名读取。

---

## 二、架构总览

```text
              匿名用户 / Internet
                      │
                      │ 匿名 GET 请求(访问对象 URL)
                      ▼
      ┌────────────────────────────────────┐
      │          S3 访问控制两层结构           │
      │                                      │
      │  第一层:Block Public Access          │
      │  (账户/桶级别总闸,决定"能不能公开")     │
      │  默认状态:全部开启(拦截一切公开访问)    │
      │                                      │
      │              需要显式关闭 ▼            │
      │                                      │
      │  第二层:Bucket Policy                │
      │  (具体授权书,决定"谁能做什么")          │
      │  需要显式声明:                        │
      │    Principal: *                      │
      │    Action: s3:GetObject              │
      │    Resource: arn:aws:s3:::bucket/*   │
      └────────────────────────────────────┘
                      │
                      ▼
        两层都放行 → 200 OK,可公开读取
        任一层未放行 → 403 AccessDenied
```

**一句话结论**
```text
允许公开访问 ≠ 已经允许公众读取
两个开关分别管"能不能"和"谁可以、能做什么"，缺一不可
```

## 四、实验步骤(通用流程)

- **步骤 1:创建 S3 存储桶并上传对象**
- **步骤 2:尝试匿名访问对象 URL,确认默认私有(AccessDenied)**
- **步骤 3:关闭 Block Public Access 四项设置**
- **步骤 4:编写并保存 Bucket Policy,授予 `Principal: *` 的 `s3:GetObject` 权限**
- **步骤 5:再次匿名访问对象 URL,验证公开可读成功**

## 五、遇到的关键问题

### 问题 1:仅关闭 Block Public Access,未配置 Bucket Policy,导致依然 AccessDenied

**现象**:按教程关闭 Block Public Access 的四个选项后,再次匿名访问对象 URL,浏览器依然显示 `AccessDenied`
**原因**:关闭 Block Public Access 只是解除了"公开访问不可能发生"这个账户/桶级别的硬性拦截,S3 默认仍然不会主动授予匿名 Principal 任何读取权限——这一步和"授权"是两回事
**解决**:额外编写 Bucket Policy,显式授予 `Principal: *` 的 `s3:GetObject` 权限,针对目标对象重新测试,访问成功
**收获**:两个权限开关的职责不同——Block Public Access 是"总闸",控制这件事有没有可能发生;Bucket Policy 是"具体授权书",控制谁、能做什么。参照的教程录制较早,当时的默认策略可能和现在不一样,遇到"照着做却达不到预期效果"时,应该先假设默认策略变了,再针对性排查具体差了哪一层权限

---

## 六、结论与心得

1. **核心结论**:S3 的公开访问控制是分层设计的——账户/桶级别的 Block Public Access 决定"可能性",Bucket Policy 决定"具体授权"。这个"总闸 + 具体授权"的两层结构,后续在 CloudFront + OAC 实验里也会以另一种形式出现(OAC 收紧的正是 Bucket Policy 这一层)。
2. **老教程要辩证参照**:视频教程录制时间和现在的默认安全策略可能不一致,遇到"照着做却达不到预期效果"时,先假设是策略默认值变了,而不是自己操作错了,再针对性排查具体差了哪一层权限。
3. 这次的排查方法论和之后 EFS 实验的思路是一致的:**先分清卡住的是"能不能"这个开关,还是"允许谁"这个授权**,这个判断顺序比死记具体报错更通用。
