# EFS 挂载 EC2 实验记录

> Region:eu-west-1 | 课程对应:Kevin LYU Udemy 课程 · 存储篇 EFS

---

## 一、实验目标

验证 EFS 作为跨实例共享的网络文件系统,通过 NFS 协议挂载到 EC2 上使用。核心排查重点是安全组这一层——EC2 与 EFS 挂载目标分属不同的安全组时,NFS(2049)端口是否被正确放行,延续此前实验里"钥匙 vs 路"的排查框架。

---

## 二、架构总览

```text
                        VPC (vpc-0e7ab509a95203dca)
      ┌────────────────────────────────────────────────────────────┐
      │                                                              │
      │   ┌───────────────────┐        NFS / TCP 2049   ┌────────────────────┐
      │   │     EC2 实例        │ ───────────────────────▶│   EFS 挂载目标        │
      │   │    (t3.micro)       │                         │  (每个 AZ 一个)       │
      │   │                     │                         │                      │
      │   │   安全组 A           │                         │   安全组 B            │
      │   │   sg-0666b0be...     │                         │   sg-0b8d0237...      │
      │   │  (launch-wizard-4)   │                         │    (default)          │
      │   └───────────────────┘                         └────────────────────┘
      │            │                                                │
      │            │      安全组 B 的入站规则需要显式引用                │
      │            └────── 安全组 A 作为 Source,放行 NFS(2049) ───────┘
      │                                                              │
      └────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
                            ┌───────────────────────┐
                            │      EFS 文件系统        │
                            │   fs-0eaf726fd241a3802  │
                            └───────────────────────┘
```

**核心关系**
```text
EC2 的安全组 与 EFS挂载目标的安全组 是两个独立的组，不需要"一致"
NFS(2049) 能否放行，取决于安全组B 有没有把 安全组A 加入信任来源(Source)
这个信任关系是单向的引用，不是把两边改成同一个安全组
```

## 四、实验步骤(通用流程)

- **步骤 1:确认 EFS 文件系统与挂载目标已创建,覆盖 EC2 所在的可用区**
- **步骤 2:确认 EC2 实例已启动,且与 EFS 挂载目标处于同一 VPC**
- **步骤 3:在 EC2 上创建本地挂载点目录**
- **步骤 4:执行 NFS 挂载命令**
- **步骤 5:检查安全组配置——确认 EFS 挂载目标的安全组入站规则,是否放行来自 EC2 安全组的 NFS(2049) 流量**
- **步骤 6:若未放行,在 EFS 挂载目标的安全组新增入站规则,来源(Source)引用 EC2 的安全组 ID**
- **步骤 7:重新挂载,通过 `df -h` 验证挂载成功**
- **步骤 8:进入挂载点目录,执行写入/读取测试,验证 EFS 可正常读写**

## 五、遇到的关键问题

### 问题 1:安全组不匹配,导致 NFS 连接超时

**现象**:挂载点目录已就绪的情况下,执行 mount 命令卡住直到 `mount.nfs4: Connection timed out`
**原因**:先排查 VPC、子网、可用区,确认 EC2 和 EFS 挂载目标处于同一 VPC、且 EC2 所在 AZ 确实有对应的挂载目标,这几项都正常。进一步比对安全组发现:EC2 使用的是自定义安全组 `launch-wizard-4`(仅放行 SSH/HTTP),EFS 挂载目标使用的是 VPC 的 default 安全组(仅信任"挂着同一个 default SG 的资源"),两者不是同一个组,导致 NFS 端口(2049)没有被放行
**解决**:在 EFS 挂载目标的安全组上新增一条入站规则——类型 NFS,来源(Source)引用 EC2 的安全组 ID,而不是修改 EC2 的安全组本身
**收获**:`Connection timed out` 指向的是网络/权限层,不是"网络完全不通",而是"通路存在但没被放行"。诊断顺序应该是先确认网络路径(VPC/AZ/挂载目标)全部正常,再锁定到安全组这一层做精确修复;修复方式上,安全组不需要"改成一致",只需要被访问方(EFS)的安全组显式引用来源方(EC2)的安全组作为 Source,这样改动范围最小,也符合最小权限原则

---

## 六、结论与心得

1. **核心结论**:这次 timeout 的根因不是网络不通,而是安全组没有放行——这是"钥匙 vs 路"框架的又一次应用:VPC/子网/AZ(路)全部正常,卡住的是安全组(钥匙)这一层。
2. **安全组修复原则**:遇到跨资源访问超时,优先怀疑安全组不匹配,但修复方式不是把两边改成"同一个安全组",而是让被访问方的安全组精确引用来源方的安全组 ID 作为 Source——这样改动范围最小,也符合最小权限原则。
3. **报错分类诊断法**:本地文件系统层面的报错和网络/权限层面的报错,排查方向完全不同,先判断报错属于哪一层,再决定往哪个方向查,比盲目试错更高效。这个方法论和之前 S3 实验里"先分清是 Block Public Access 还是 Bucket Policy 缺失"是同一类思路的延伸。
