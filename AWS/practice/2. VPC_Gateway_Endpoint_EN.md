# VPC Gateway Endpoint for S3 Access Lab Notes

> Region: eu-west-1 | Course reference: Kevin LYU's Udemy course · Networking module, VPC Endpoint

---

## 1. Lab Objective

This lab verifies a core conclusion: **IAM permissions** and **network path** are two entirely independent mechanisms — accessing S3 requires both to be satisfied simultaneously.

- IAM role = "do I have permission" (the key)
- Network route = "can the packet actually get there" (the road)
- Gateway Endpoint = builds a route from a private subnet to S3 that never leaves AWS's internal network — **free of charge**, and fundamentally just one more entry in a route table

## 4. Lab Steps (General Procedure)

- **Step 1: Create the VPC, public/private subnets, IGW, and configure route tables (deliberately not configuring a NAT gateway for the private subnet, to make the experiment's contrast visible)**
- **Step 2: Create an EC2 Instance Connect Endpoint in the private subnet for test access**
- **Step 3: Launch both EC2 instances; create an IAM role (trusted entity: EC2, attached policy `AmazonS3FullAccess`) and attach it to both instances**
- **Step 4 (Before test): Run `aws s3 ls` on the private EC2 instance, confirming the "IAM has permission but the network can't get there" symptom (the command hangs/times out)**
- **Step 5: Create an S3 Gateway Endpoint — under service category choose AWS services, search for `com.amazonaws.<region>.s3`, and make sure to pick the Gateway type (not Interface); associate it with the private subnet's route table**
- **Step 6 (After test): Re-run `aws s3 ls` on the private EC2 instance, confirming an immediate success; check the route table to confirm a new S3 prefix list → vpce-xxx route has appeared**

## 5. Key Issues Encountered

Recorded in the order they actually occurred — 3 key issues total.

### Issue 1: Mistook an EC2 Instance Connect Endpoint for an S3 Gateway Endpoint (the biggest pitfall in this lab)

**Symptom**: Believed the "create a Gateway Endpoint" step was already done, but the After test hung exactly the same way as the Before test
**Cause**: Checking the private subnet's route table showed no `pl-xxx → vpce-xxx` route. Going back to check the previously created "endpoint" revealed its ID prefix was `eice-`, meaning it was an **EC2 Instance Connect Endpoint**, not a `vpce-`-prefixed **VPC Gateway Endpoint**. This endpoint had actually been created earlier for SSH access to the private EC2 instance and had nothing to do with S3 — its name (`end-point-s3`) was simply misleading. The two also have separate creation entry points: EIC Endpoints live under the "EC2 Instance Connect Endpoints" menu, while Gateway Endpoints live under the "Endpoints" menu
**Resolution**: Went to the correct "Endpoints" menu and created an actual S3 Gateway Endpoint, correctly associated with the private subnet's route table
**Takeaway**: Resource naming should precisely reflect what a resource actually is — don't infer function from a name alone. The two endpoint types serve entirely different purposes (connection management vs. private routing) despite similar-sounding names. When something "was supposedly created but isn't working," the first move should be to go back and verify the resource's actual type

---

### Issue 2: Almost created an IAM user instead of a role

**Symptom**: Was about to run `aws configure` on pri-ec2, intending to manually enter an Access Key
**Cause**: Clarified the fundamental difference between an IAM user and an IAM role — a user corresponds to long-lived static credentials that need to be manually managed and rotated; a role corresponds to temporary credentials automatically issued and rotated by the metadata service, tied to the instance's lifecycle
**Resolution**: Interrupted `aws configure`, and instead created an IAM role and attached it to the EC2 instance, introducing no static credentials at all
**Takeaway**: The standard way for EC2 to access AWS services is via an attached IAM role, not a configured user's static keys — this is a practical confirmation of the principle "long-lived Access Keys have no place in production"

---

### Issue 3: `aws s3 ls` still hung even after confirming the role was working correctly (the verification method itself was flawed)

**Symptom**: After rebuilding the environment, used curl to query the metadata service and confirmed the role was attached correctly, but `aws s3 ls` still didn't respond
**Cause**: Realized "querying the metadata service" and "`aws s3 ls`" are two entirely different kinds of calls — the former is a local link (169.254.169.254) that never goes through VPC routing, and only proves the role is attached correctly; the latter, even after the role check passes, still has to make a real network request to the S3 endpoint, and that step still has to travel through the private subnet's route table. In this particular rebuilt environment, the Gateway Endpoint hadn't been recreated yet
**Resolution**: Went back to Step 5, recreated the S3 Gateway Endpoint and correctly associated it with the private subnet's route table — problem resolved, `aws s3 ls` returned immediately and successfully listed `leon-s3-new`
**Takeaway**: Verifying whether an IAM role is working shouldn't rely solely on a command that triggers a network request (like `aws sts get-caller-identity` or `aws s3 ls`) — a purely local metadata query should be used to verify that separately. Whether the role is correct and whether the network is reachable are always two independent links that need to be verified separately — this is the core conclusion this lab kept reinforcing

## 6. Conclusions and Takeaways

1. **Core conclusion**: `IAM permissions + network routing` are two independent, necessary conditions for accessing AWS services — failing to satisfy either causes failure, and the two failure modes look completely different (a permission issue is a fast rejection, a network issue is a hang/timeout).
2. **Troubleshooting methodology**: When diagnosing connectivity, use a tool that matches the target protocol (curl for HTTPS, not ping); when diagnosing permissions, use a local metadata query that doesn't trigger a network request (note that newer EC2 instances default to requiring IMDSv2, which means fetching a token before querying) — this keeps permission-layer and network-layer issues from getting tangled together in the diagnosis.
3. **The biggest lesson**: Similarly named or similar-sounding AWS console resource types are easy to confuse (EC2 Instance Connect Endpoint vs. VPC Gateway Endpoint) — resource naming should precisely reflect the actual type. When something "was supposedly created but isn't working," the first instinct should be to go back and verify the resource's actual type, rather than continuing to chase the symptom downstream.

## 7. Key Command Reference

```bash
# Metadata query (IMDSv2)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/

# Network connectivity test (a substitute for ping, since S3 uses HTTPS, not ICMP)
curl -v --max-time 5 https://s3.<region>.amazonaws.com

# S3 verification
aws s3 ls
aws s3 cp test.txt s3://<bucket-name>/
```
