# S3 Public Access Lab Notes

> Region: eu-west-1 | Course reference: Kevin LYU's Udemy course · Storage module, S3

---

## 1. Lab Objective

This lab verifies a permission concept that's easy to conflate: **"disabling Block Public Access" ≠ "already granting public read access"**. These are two independent switches that each control a different thing — one determines whether public access can happen at all (a bucket/account-level hard block), and the other determines who is specifically allowed to do what (the Bucket Policy's actual grant). Both must be satisfied together before an object can be read anonymously from the public internet.

---

## 2. Architecture Overview

```text
              Anonymous user / Internet
                      │
                      │ Anonymous GET request (object URL)
                      ▼
      ┌────────────────────────────────────┐
      │       S3's Two-Layer Access Control   │
      │                                      │
      │  Layer 1: Block Public Access        │
      │  (bucket/account-level master switch, │
      │   determines "can this happen at all")│
      │  Default: fully enabled (blocks all   │
      │  public access)                       │
      │                                      │
      │           must be explicitly disabled ▼│
      │                                      │
      │  Layer 2: Bucket Policy              │
      │  (the specific grant, determines      │
      │   "who's allowed to do what")         │
      │  Must be explicitly declared:          │
      │    Principal: *                      │
      │    Action: s3:GetObject              │
      │    Resource: arn:aws:s3:::bucket/*   │
      └────────────────────────────────────┘
                      │
                      ▼
        Both layers open → 200 OK, publicly readable
        Either layer closed → 403 AccessDenied
```

**One-line conclusion**
```text
Allowing public access ≠ already granting public read access
The two switches govern "can it happen" and "who's allowed, to do what"
— both are required, neither is optional
```

## 4. Lab Steps (General Procedure)

- **Step 1: Create the S3 bucket and upload an object**
- **Step 2: Attempt anonymous access to the object URL, confirming the default private state (AccessDenied)**
- **Step 3: Disable all four Block Public Access settings**
- **Step 4: Write and save a Bucket Policy granting `Principal: *` the `s3:GetObject` permission**
- **Step 5: Re-attempt anonymous access to the object URL, confirming public read now succeeds**

---

## 5. Key Issue Encountered

### Issue 1: Disabling Block Public Access alone, without configuring a Bucket Policy, still resulted in AccessDenied

**Symptom**: After disabling all four Block Public Access settings as the tutorial instructed, anonymously accessing the object URL still returned `AccessDenied`
**Cause**: Disabling Block Public Access only removes the account/bucket-level hard block that made public access *impossible* — S3 still doesn't automatically grant any read access to an anonymous principal by default. This step and "granting access" are two separate things
**Resolution**: Additionally wrote a Bucket Policy explicitly granting `s3:GetObject` to `Principal: *`, then retested against the target object — access succeeded
**Takeaway**: The two permission switches serve different roles — Block Public Access is the "master switch" controlling whether something is possible at all; the Bucket Policy is the "specific grant" controlling who is allowed to do what. The tutorial being followed was recorded on an older version of the platform, whose default policy behavior may have differed from today's — when "following the steps exactly" doesn't produce the expected result, first assume a default setting has changed, then investigate which specific permission layer is actually missing

## 6. Conclusions and Takeaways

1. **Core conclusion**: S3's public access control is layered by design — the bucket/account-level Block Public Access setting determines *possibility*, and the Bucket Policy determines the *specific grant*. This "master switch + specific grant" two-layer structure shows up again later in the CloudFront + OAC lab, in a different form (OAC tightens exactly this Bucket Policy layer).
2. **Older tutorials need to be applied critically**: A video tutorial's recording date and the platform's current default security posture may not match. When "following the steps exactly" doesn't produce the expected result, first assume a default setting has changed, rather than assuming you made an operational mistake — then investigate which specific permission layer is actually missing.
3. This troubleshooting methodology is consistent with the approach used later in the EFS lab: **first identify whether what's blocking you is the "can it happen at all" switch, or the "who's allowed" grant** — that ordering is more broadly useful than memorizing specific error messages.
