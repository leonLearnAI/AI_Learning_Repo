# EFS Mounted to EC2 Lab Notes

> Region: eu-west-1 | Course reference: Kevin LYU's Udemy course · Storage module, EFS

---

## 1. Lab Objective

This lab verifies EFS as a network file system shared across instances, mounted onto an EC2 instance over the NFS protocol. The core troubleshooting focus is the security group layer — when EC2 and the EFS mount target belong to different security groups, whether the NFS (2049) port is correctly allowed through — continuing the "key vs. road" diagnostic framework from earlier labs.

**Core relationship**
```text
EC2's security group and the EFS mount target's security group are
two independent groups — they don't need to "match"
Whether NFS(2049) is allowed through depends on whether Security
Group B has added Security Group A as a trusted Source
This trust relationship is a one-directional reference,
not making both sides the same security group
```

## 4. Lab Steps (General Procedure)

- **Step 1: Confirm the EFS file system and mount targets already exist, covering EC2's availability zone**
- **Step 2: Confirm the EC2 instance is running and in the same VPC as the EFS mount target**
- **Step 3: Create a local mount point directory on EC2**
- **Step 4: Run the NFS mount command**
- **Step 5: Check the security group configuration — confirm whether the EFS mount target's security group inbound rules allow NFS(2049) traffic from EC2's security group**
- **Step 6: If not allowed, add a new inbound rule to the EFS mount target's security group, referencing EC2's security group ID as the Source**
- **Step 7: Re-mount, and confirm success via `df -h`**
- **Step 8: Enter the mount point directory and run a write/read test to confirm EFS works correctly**

## 5. Key Issue Encountered

### Issue 1: Security group mismatch caused the NFS connection to time out

**Symptom**: With the mount point directory already in place, running the mount command hung until it returned `mount.nfs4: Connection timed out`
**Cause**: First checked the VPC, subnet, and availability zone — confirmed EC2 and the EFS mount target were in the same VPC, and that EC2's AZ had a corresponding mount target; all of these checked out fine. Comparing the two sides' security groups further revealed that EC2 was using a custom security group, `launch-wizard-4` (only allowing SSH/HTTP), while the EFS mount target used the VPC's default security group (which only trusts resources sharing that same default SG) — the two were not the same group, so the NFS port (2049) had never been allowed through
**Resolution**: Added a new inbound rule to the EFS mount target's security group — type NFS, with the Source referencing EC2's security group ID, rather than modifying EC2's security group itself
**Takeaway**: `Connection timed out` points to the network/access layer — it doesn't mean "the network is completely unreachable," it means "a path exists but wasn't allowed through." The right diagnostic order is to first confirm the network path (VPC/AZ/mount target) is entirely normal, then narrow in on the security group layer for a precise fix. On the fix itself: security groups don't need to be made "the same" — the receiving side (EFS) simply needs its security group to explicitly reference the source side's (EC2's) security group as the Source. This keeps the change scope minimal and follows the principle of least privilege

---

## 6. Conclusions and Takeaways

1. **Core conclusion**: The root cause of the timeout wasn't an unreachable network — it was a security group that hadn't been opened up. This is another application of the "key vs. road" framework: VPC/subnet/AZ (the road) were all fine; what was blocking access was the security group (the key).
2. **Security group fix principle**: When cross-resource access times out, security group mismatch should be the prime suspect — but the fix isn't to make both sides "the same security group." It's to have the receiving side's security group precisely reference the source side's security group ID. This keeps the change scope minimal and follows the principle of least privilege.
3. **Error classification diagnostics**: Local filesystem-level errors and network/access-layer errors point in completely different troubleshooting directions — figure out which layer an error belongs to first, rather than trial-and-erroring blindly. This methodology extends the same approach used in the earlier S3 lab: "first identify whether the issue is Block Public Access or a missing Bucket Policy."

## 7. Checklist

- [ ] EFS file system created, with mount targets covering EC2's availability zone
- [ ] EC2 and the EFS mount target confirmed to be in the same VPC
- [ ] The EFS mount target's security group allows NFS(2049), with the source referencing EC2's security group (rather than being changed to match the same group)
- [ ] Mount point directory created on EC2
- [ ] The mount command ran successfully, and `df -h` shows the EFS file system mounted
- [ ] Created a test file **inside** the mount point directory (not on local disk) and verified read/write actually works
- [ ] (Optional) To verify EFS's core selling point — cross-instance sharing — spin up a second EC2 instance, mount the same EFS file system, and confirm the same file is visible from there too
