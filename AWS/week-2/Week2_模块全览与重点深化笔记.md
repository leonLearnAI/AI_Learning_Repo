# 模块三:计算(共 9 项)

## 3.1 全部 9 项服务简介

### ★★★ Amazon EC2
**云中的虚拟服务器**

EC2 是亚马逊提供的弹性计算服务,允许用户租用虚拟服务器(称为实例)来运行各种应用程序。实例可以根据需求灵活扩展和收缩,用户可以按自己的需求选择不同类型的实例(计算优化、存储优化、内存优化等)来满足不同应用的性能需求,并且可以在实例上部署任意操作系统和应用程序,完全掌控实例的配置和管理,按实际使用的资源和时间付费。EC2 是构建和托管各类云计算工作负载的核心基础设施之一。

**案例**:一家初创公司用 EC2 托管网站,一部分实例跑前端服务、一部分跑数据库,可以根据网站流量灵活调整实例数量;同时也用 EC2 的弹性算力临时拉起一个数据处理集群,批量分析完市场调研数据后就把实例停掉,避免不必要的成本。

### ★★★ AWS Auto Scaling
**自动增减资源数量**

Auto Scaling 按你设定的策略(比如 CPU 使用率超过 70% 就加实例、低于 30% 就减实例)自动增加或减少 EC2 等资源的数量,让应用始终保持"刚好够用"的资源水平——流量突增时不会扛不住,流量低谷时也不会为闲置资源多付钱。它支持三种扩缩容方式:目标追踪(盯住一个指标自动调节)、步进扩缩容(按阈值分级调整)、计划扩缩容(提前排好特定时间点该扩容)。

**案例**:一个电商网站配置目标追踪策略盯住 CPU 使用率,大促期间流量暴涨时自动多开几十台实例扛压力,大促结束流量回落后自动把多余实例关掉。

### ★★☆ AWS Batch
**大规模批处理任务调度**

Batch 自动管理运行批处理计算任务所需的计算资源——你只需要提交任务(比如"处理这 1000 个文件"),它自动决定用多少台、什么类型的机器来跑,任务跑完自动释放资源,不用手动管理这些资源的生命周期。

**案例**:一家医学影像公司每天要对几万张影像做批量分析,提交任务给 Batch 后,系统自动调度足够的计算资源并行处理,处理完毕自动释放。

### ★★★ AWS Elastic Beanstalk
**应用即服务的部署平台**

Elastic Beanstalk 让你只需上传应用代码,就能自动完成底层基础设施的部署——EC2 实例、负载均衡、Auto Scaling、监控这些都自动配好,不用一项项手动搭建,但底层资源依然可以查看和精细调整,不像更"黑盒"的 Serverless 方案那样完全看不见底层。

**案例**:一个小团队想快速上线一个 Web 应用,又不想从零手动配置负载均衡这些基础设施,用 Elastic Beanstalk 上传代码包后几分钟就能跑起来一套完整的可伸缩部署。

### ★★★ Amazon Lightsail
**简化版云主机,适合入门和小型项目**

Lightsail 提供打包好的、价格固定、配置简单的虚拟服务器套餐(包含计算、存储、网络流量),特别适合不需要复杂云架构知识的场景。它的定位介于"传统虚拟主机"和"完整的 EC2"之间,配置更简单、价格更容易预估,但灵活性和可扩展性不如直接用 EC2。

**案例**:一个自由职业者想搭个人作品集网站,不需要复杂云架构,直接选 Lightsail 一个固定月付套餐,几分钟就有一台配好的服务器可以部署网站。

### ★★★ AWS Lambda
**无服务器函数计算**

*(本周 Day 8–9 深化讲过,详见 3.2 节展开,这里从略)*

### ☆☆☆ AWS Outposts
**把 AWS 基础设施搬到你自己的机房**

Outposts 把 AWS 的软硬件设施实际部署到客户自己的数据中心里,让你能在本地机房用和 AWS 云上一模一样的 API 和工具,同时满足数据必须留在本地的合规要求。

**案例**:一家银行因监管要求核心数据不能离开自己的数据中心,又想用 AWS 的开发工具和 API 体验,采购 Outposts 设备部署在自己机房里,本地处理数据的同时保持和云上一致的操作体验。

### ☆☆☆ AWS Wavelength
**把计算能力部署到 5G 网络边缘**

Wavelength 把 AWS 计算和存储资源部署在电信运营商的 5G 网络边缘,让终端用户的请求不用绕经很远的 AWS 区域,直接在离用户很近的网络边缘处理,适合对延迟极其敏感的应用。

**案例**:一款需要超低延迟的 AR/VR 应用,用 Wavelength 把关键计算部署在离用户最近的 5G 边缘节点,大幅减少端到端响应延迟。

### ☆☆☆ AWS Local Zones
**把 AWS 区域延伸到更靠近你的城市**

Local Zones 是 AWS 区域的延伸站点,部署在大城市附近,让那些对延迟敏感、又不想绑定 Wavelength 那种电信运营商 5G 网络方案的应用,能有一个离用户更近的计算节点可用。

**案例**:一家影视后期制作公司需要极低延迟处理大文件渲染,用离自己办公室最近的 Local Zone 而不是主区域,减少了网络传输延迟。

## 3.2 本周深化的重点:Lambda 与计算选型(Day 8–9)

**① Lambda 深度(Day 8)**
- 冷启动是执行环境重新创建+运行时启动+函数外初始化逻辑跑一遍的总耗时,CPU/内存分配、代码包大小、语言类型、是否挂 VPC 都会影响冷启动时长
- **预置并发**:花钱让执行环境提前热身,跳过冷启动;**预留并发**:给函数划专属并发配额,不被别的函数抢——两者管的是完全不同的事,可以同时配也可以只配一个
- 并发默认是**整个账号共享一个池子**(默认上限 1000),某个函数流量暴涨会挤占别的函数的额度,导致后者被节流
- **15 分钟硬上限**:能拆分的长任务用 Step Functions 接力编排,拆不开(需要长连接/复杂状态)的换成 Fargate
- **响应流式(Response Streaming)**:让用户"感觉立刻开始回答",而不是盯着空白等到底;目前只能通过 **Function URL** 触发,API Gateway 不支持流式转发
- **Layers**(总大小上限 250MB,适合轻量共用依赖)vs **容器镜像部署**(上限 10GB,适合重型依赖或已有 Docker 镜像)

**② 计算选型(Day 9)**
- 选择光谱:事件驱动/能接受冷启动/单次有限时→Lambda;常驻/长连接/无严格时长(尤其 Agent 框架)→Fargate;快速部署容器化 Web 服务不折腾编排→App Runner(★注:课程截图 9 项服务里没有这一项,是确认的缺口);需要操作系统级控制权或 GPU→EC2
- **GPU 实例**:G 系列给"推理"(模型已训练好,拿去回答问题),P 系列给"训练"(从零训练或大规模微调);调用 Bedrock 这类托管模型服务完全不用操心 GPU,只有自部署模型才需要自己选
- **Graviton(ARM 架构)**:同规格通常比 x86 便宜约 20%,但不是所有软件/容器镜像都原生支持 ARM,上之前要确认整条技术栈兼容

## 3.3 架构图/流程(文字描述)

**排查"用户反馈 AI 应用第一次总是很慢"的三个方向**
```
① 查 CloudWatch Logs 的 REPORT 行,有没有 Init Duration → 有则确认是 Lambda 冷启动
② 若挂了 VPC,对比同类未挂 VPC 函数的 Init Duration → 差异明显则是 ENI 建立开销
③ 若 Init Duration 很短但整体 Duration 依然很长 → 问题在下游依赖(数据库/Bedrock等),不在 Lambda 本身
```

**计算方式选型判断路径**
```
事件驱动、能接受冷启动、单次执行有限时 → Lambda
需要常驻、长连接、无严格时长限制(尤其 Agent 框架) → Fargate
只想快速部署容器化 Web 服务,不折腾编排配置 → App Runner
需要操作系统级控制权,或需要 GPU(推理选G系列/训练选P系列) → EC2
```

# 模块四:容器(共 4 项)

## 4.1 全部 4 项服务简介

### ★★★ Amazon ECS(Elastic Container Service)
**AWS 原生的容器编排服务**

ECS 帮你管理和调度一批 Docker 容器,决定这些容器该跑在哪些资源上、怎么做健康检查和自动重启。它是 AWS 自己设计的编排系统,跟 AWS 其他服务(ALB、CloudWatch、Fargate)集成非常顺滑,配置和学习曲线也比 Kubernetes 更平缓。

**案例**:一个团队把应用拆成好几个微服务容器,用 ECS 统一编排管理这些容器的部署、伸缩和健康检查,不用手动一个个管理。

### ★★★ Amazon EKS(Elastic Kubernetes Service)
**托管版 Kubernetes**

EKS 是 AWS 托管的 Kubernetes 服务,用的是业界标准、跨云厂商通用的容器编排技术。相比 ECS,EKS 配置更复杂,但换来更强的可移植性和更丰富的开源生态,适合团队本身有 Kubernetes 经验,或需要多云部署避免被单一云厂商锁定的场景。

**案例**:一家已经在其他云厂商上用 Kubernetes 管理容器的公司迁移到 AWS 后,选择 EKS 而不是 ECS,因为团队原有的 Kubernetes 配置和工具链几乎可以直接复用。

### ★★★ Amazon ECR(Elastic Container Registry)
**托管的容器镜像仓库**

ECR 是存放 Docker 容器镜像的托管仓库,跟 ECS、EKS、Lambda 都无缝集成,支持镜像版本管理和漏洞扫描。构建好镜像推送到 ECR,后续部署时直接从这里拉取,不用自己搭建和维护镜像仓库服务。

**案例**:一个团队的 CI/CD 流水线在每次代码提交后自动构建新镜像并推送到 ECR,部署时 ECS 直接从 ECR 拉取最新镜像进行更新。

### ★★★ AWS Fargate
**无服务器容器运行环境**

*(本周 Day 9 深化讲过,详见 4.2 节展开,这里从略)*

## 4.2 本周深化的重点:Fargate 与 ECS/EKS 选型(Day 9)

- Fargate 是"无服务器但常驻"——不用管底层 EC2 主机,但跑的是一个一直挂着的容器,没有 15 分钟这道墙,能维持长连接,代价是不像 Lambda 那样零请求零花费,容器一直跑就一直计费
- Agent 框架的运行时首选 Fargate:长连接 + 复杂依赖 + 需要维持内存中状态,这个组合天然适合常驻容器,而不是"来一次跑一次"的 Lambda
- ECS vs EKS 的判断标准是**要不要多云、团队有没有 Kubernetes 积累**,不是看谁"更好"——没有这两条理由,ECS 通常更省心

# 模块五:存储(共 7 项)

## 5.1 全部 7 项服务简介

### ★★★ Amazon EBS(Elastic Block Store)
**挂载在 EC2 上的块存储**

EBS 是给 EC2 实例用的持久化块存储卷,就像给虚拟机挂一块硬盘,数据在实例停止或重启后依然保留。支持不同性能等级(通用型 SSD、高性能 IOPS 优化型),适合需要低延迟、高吞吐量随机读写的场景,比如数据库的存储层。

**案例**:一个跑 MySQL 数据库的 EC2 实例,把数据文件存在一块高性能 EBS 卷上,即使这台 EC2 重启,数据依然完整保留在这块卷里。

### ★★★ Amazon EFS(Elastic File System)
**弹性文件存储,可被多台机器同时挂载**

EFS 提供基于 NFS 协议的共享文件系统,容量自动伸缩,最大特点是**可以被多个 EC2 实例(甚至 Lambda)同时挂载读写**,这是 EBS 做不到的(EBS 通常只能挂载给一台实例)。适合需要多台机器共享同一份文件的场景。

**案例**:一个视频处理集群有多台 EC2 实例需要同时读取同一批源文件,用 EFS 挂载给所有实例,大家共享同一份存储,不用各自复制一份。

### ★★☆ Amazon FSx
**托管的第三方文件系统**

FSx 提供几种主流第三方文件系统的托管版本(Windows File Server、Lustre 高性能计算文件系统、NetApp ONTAP 等),适合本来就依赖这些特定文件系统技术、迁移上云又不想改造应用的场景。

**案例**:一家企业的 Windows 应用长期依赖 Windows File Server 做文件共享,上云时用 FSx for Windows File Server,应用代码完全不用改动就能直接用云上的托管版本。

### ★★★ Amazon S3
**对象存储**

*(本周 Day 11 深化讲过,详见 5.2 节展开,这里从略)*

### ★★★ Amazon S3 Glacier
**超低成本的归档存储**

Glacier 是 S3 旗下专为"很少访问、但必须长期保留"的数据设计的存储类型,价格比标准 S3 便宜得多,代价是取回数据需要额外时间(几分钟到几小时不等)和取回费用。常用于合规要求的长期数据留存。

**案例**:一家医疗机构需要按法规保留病历记录 7 年以上,这些记录几乎不会被访问,存进 Glacier Deep Archive,存储成本压到最低,同时满足合规留存要求。

### ★★☆ AWS Storage Gateway
**打通本地和云端存储的混合云网关**

Storage Gateway 让本地数据中心的应用可以像访问本地存储一样访问 AWS 云存储,本质是在本地部署一个网关设备,把请求转换成对 S3 等云存储的调用,同时在本地缓存热数据加速访问。

**案例**:一家企业想把本地文件服务器逐步迁移到云上,又不想一次性中断本地应用,用 Storage Gateway 让本地应用继续以原有方式访问文件,背后数据实际已经在向 S3 同步。

### ★★☆ AWS Backup
**统一的备份管理服务**

Backup 让你在一个地方集中管理多种 AWS 资源(EC2、EBS、RDS、DynamoDB 等)的备份策略,可以设置备份频率、保留时长、跨区域复制这些规则统一下发,不用为每种资源分别配置各自的备份机制。

**案例**:一家企业过去分别给 EC2、RDS 各自配置备份脚本,管理很分散,改用 AWS Backup 后在一个控制台统一制定所有资源的备份计划和保留策略。

## 5.2 本周深化的重点:S3 核心机制(Day 11)

- **事件通知四种下游**:单一处理逻辑用 Lambda,要削峰缓冲用 SQS,一个事件多方广播用 SNS,复杂过滤/路由用 EventBridge
- **预签名 URL**:后端生成一个带签名、有时效、权限受限的临时链接,前端拿着直接跟 S3 对话,文件不经过后端服务器——但它本身**不含"上传完自动通知谁"的能力**,要配合事件通知才能实现完整流程
- **加密四选一**:SSE-S3(全托管、免费)、SSE-KMS(可审计、企业合规问卷最常要求)、SSE-C(客户自己管密钥)、DSSE-KMS(双重加密,顶格合规场景)
- **版本控制 + 生命周期规则**:删除只是打删除标记,历史版本仍在;生命周期规则负责把旧版本自动转冷存储或彻底清理,控制成本
- **强一致性**:2020 年 12 月后 S3 所有操作(新建/覆盖/删除)都是强一致性,写完立刻读能保证读到最新内容,不用再为"读到旧内容"写防御性重试逻辑

## 5.3 架构图/流程(文字描述)

**用户上传 PDF → 自动触发处理**
```
前端向后端要一个预签名 URL → 前端直接 PUT 文件到 S3(不经过后端服务器)
→ 额外配置 S3 事件通知(比如触发 Lambda)→ Lambda 被唤醒,读取这个 PDF 做处理(比如调 Textract)
→ 处理结果存回 S3 或写入数据库 → 前端轮询状态或另外接一个通知机制得知处理完成
```

## 6.2 本周深化的重点:关系型数据库、向量存储与 DynamoDB/缓存(Day 12–13)

**① 关系型数据库与向量存储(Day 12)**
- **多可用区 vs 只读副本**:多可用区备库是"备胎"(平时不可读,故障才接管,管高可用);只读副本是"能上路的车"(可读,专门分流读请求,管读扩展)
- **Aurora 存储计算分离**:存储层跨 3 个可用区自动维护 6 份副本,带来更快的故障恢复(秒级)和更快的副本创建速度
- **Aurora Serverless v2**:以 **0.5 ACU** 为颗粒度秒级伸缩、不中断连接,最低可配置到 **0 ACU** 自动暂停(约 15 秒唤醒延迟)
- **pgvector**:不是独立产品,是 PostgreSQL 的扩展插件,寄生在已有的 Aurora 账单和运维经验里,是 RAG 向量库最省钱的选择
- **IVFFlat vs HNSW**:前者建索引快、省内存但精度对分簇数敏感;后者查询快、精度普遍更高但建索引慢、占内存大,生产级场景通常优先 HNSW

**② DynamoDB 与缓存(Day 13)**
- **分区键与热分区**:分区键决定数据怎么打散存放,取值种类太少、请求集中在少数值上会导致"热分区"(个别分区被挤爆,其他分区闲置)
- **单表设计**:因为 DynamoDB 不支持 JOIN,把经常一起查询的不同类型数据用有规律的键设计塞进同一张表,一次请求就能拿到
- **Streams**:数据变动的"事件通知"机制,和 S3 事件通知同一个思路,常用来触发 Lambda 做后续动作(管"数据变了要不要自动干点什么")
- **TTL**:给数据加一个过期时间戳,到期自动清理(不是立刻删除,是启动删除流程,有延迟)
- **ElastiCache(Redis) vs MemoryDB for Redis**:前者是"丢了顶多变慢"的纯缓存层,适合语义缓存;后者是"丢了会出事"的持久化主存储,适合 Agent 会话状态

## 6.3 架构图/流程(文字描述)

**库存变动 → 自动触发预警检查(DynamoDB Streams)**
```
库存数量字段被修改 → DynamoDB Streams 捕捉到这条变动
→ 触发 Lambda → Lambda 执行库存预警检查逻辑(比如低于阈值发通知)
```

**Agent 会话状态存储选型判断**
```
问自己:"这份数据丢了,是'变慢'还是'出事'?"
→ 丢了顶多变慢(比如语义缓存,重新调一次模型) → ElastiCache
→ 丢了会出事(比如对话断片、任务上下文消失) → MemoryDB for Redis
```

# 补充:Day 10 涉及的联网服务深化

Day 10(流量入口与 LLM 流式)涉及的 API Gateway 已经在第一周笔记的"联网和内容分发"模块里做过完整介绍,这里只补充本周新讲的部分,以及两个状态需要说明的服务。

**API Gateway 的 29 秒超时问题**
- REST API 功能全但贵,HTTP API 便宜快但功能少,两者都受 **29 秒硬性超时**限制
- 绕开的三条路:①用流式返回(自然不会被判定为"卡住");②换成异步模式(先返回任务 ID,后面轮询或推送通知);③换一个不受这个限制的入口(见下面 ALB)

**AWS ALB(Application Load Balancer)** ——⚠️ 课程截图信息不全,无法确认覆盖情况
- 联网模块截图里没有 ALB,但计算模块截图右下角被遮挡截断,不排除后面还有没截到的条目,这一项的课程覆盖情况目前无法 100% 确认
- 内容上:ALB 骨子里是负载均衡器,不是托管网关,默认空闲超时 60 秒且最大可调到 4000 秒,对长响应/流式非常友好;和 API Gateway 都能接 Lambda 也都能接容器,**真正的选型分界线是要不要长响应/流式,不是后端类型**

**AWS AppSync** ——已通过截图确认课程未讲(联网模块 8 项服务里没有这一项)
- 基于 GraphQL 的 Subscription(订阅)机制,前端订阅一个"频道",后端每完成一小段处理就调 Mutation 推送新内容,AppSync 自动广播给所有订阅者
- 效果上类似打字机效果,但走的是 GraphQL 订阅这条路,本质是对 WebSocket 的一层封装

**三种流式落地方式**
- **轮询**:最简单但延迟感明显,适合不追求体验的兜底场景
- **SSE(Server-Sent Events)**:服务器单向持续推送,浏览器原生支持,AWS 上通常靠 **Lambda Function URL + 响应流式**实现,是目前 LLM 打字机效果最主流的落地方式
- **WebSocket**:全双工,靠 **API Gateway 的 WebSocket API** 实现,适合需要用户中途打断模型这种双向交互场景
