# System Design

# Part 1

---

## 1. Performance vs Scalability

**Performance** — how fast the system handles a *single* request.
**Scalability** — whether the system can handle *more* requests by adding more resources.

> **Rule of thumb:**
> 
> - Slow for 1 user → **Performance** problem (bad algorithm, missing index, inefficient query)
> - Fast for 1 user, slow under heavy load → **Scalability** problem (architecture issue)

---

## 2. Latency vs Throughput

**Latency** — time to complete *one* operation.
**Throughput** — number of operations completed *per unit of time*.

> **Design goal:** Maximize throughput under *acceptable* latency.
"Acceptable" is defined by the business context, not by an absolute standard.
> 

---

## 3. Availability vs Consistency — The CAP Theorem

In a distributed system, you can only guarantee **two of the following three**:

| Letter | Full Name | Meaning |
| --- | --- | --- |
| **C** | Consistency | Every read returns the most recent write (data is accurate) |
| **A** | Availability | Every request receives a response (system is always online) |
| **P** | Partition Tolerance | System keeps running despite network failures |

> **Key insight:** Network partitions are inevitable in the real world, so **P is non-negotiable**.
The real architectural choice is always: **C vs A**.
> 

---

## 4. CP vs AP

|  | CP | AP |
| --- | --- | --- |
| Retains | Consistency + Partition Tolerance | Availability + Partition Tolerance |
| **Sacrifices** | **Availability** | **Consistency** |
| Behavior | May reject requests, but data is always accurate | Always responds, but data may be temporarily stale |
| Use cases | Bank transfers, inventory, orders, hospital systems | Social likes, view counts, shopping carts, DNS |
| Examples | HBase, MongoDB, Zookeeper | Cassandra, DynamoDB, CouchDB |

> **Memory hook:**
> 
> - CP has no A → it **sacrifices A** (availability)
> - AP has no C → it **sacrifices C** (consistency)

---

## 5. Core Principle

> **Everything is a trade-off.**
An architect's job is not to find a perfect solution, but to make the best decision given the constraints.
>

## 1. Consistency Patterns

There are three levels of consistency in distributed systems:

### Weak Consistency

After a write, reads are **not guaranteed** to see the new data. Best-effort approach.

- Data may be lost; no sync guarantee
- Use cases: VoIP calls, real-time multiplayer games, live video streaming
- Key insight: lost data is simply **not replayed** — acceptable for real-time media

### Eventual Consistency

After a write, reads **will eventually** see the new data (typically within milliseconds to seconds). Data is replicated **asynchronously**.

- Short-term inconsistency is acceptable
- Use cases: DNS propagation, email systems, social media feeds
- Key insight: all nodes **converge to the same state** over time

### Strong Consistency

After a write, reads **immediately** see the new data. Data is replicated **synchronously**.

- Write does not return until all replicas are updated
- Use cases: bank accounts, relational databases (RDBMS), file systems
- Key insight: at any moment, every read returns the **latest correct value**

|  | Weak | Eventual | Strong |
| --- | --- | --- | --- |
| Read after write | May miss | Will catch up | Always latest |
| Replication | None | Async | Sync |
| Performance | Highest | High | Lower |
| Use case | Real-time media | DNS, social | Banking, RDBMS |

---

## 2. Availability Patterns

Two complementary patterns for achieving high availability: **Fail-over** and **Replication**.

### Fail-over

### Active-Passive (Cold Standby)

- Only the **active** server handles traffic
- The **passive** server stays on standby, monitored via **heartbeat**
- On failure: passive takes over the active's IP and resumes service
- Disadvantage: standby resources are wasted; **brief downtime** during switchover

### Active-Active (Hot Standby)

- **Both** servers handle traffic simultaneously, load is shared
- On failure: the surviving server absorbs all traffic
- Disadvantage: requires data sync between nodes; **higher complexity**

### Replication

Distributes data across multiple machines to prevent data loss.

- **Master-Slave**: master handles writes; slaves handle reads; async replication to slaves
- **Master-Master**: all nodes handle reads and writes; sync with each other

*(Deep dive in Batch 5 — Database)*

## 3. Availability in Numbers

Availability is measured in **"nines"**:

| Level | Availability | Downtime / year | Downtime / month |
| --- | --- | --- | --- |
| Three nines | 99.9% | 8h 46m | 43m 50s |
| Four nines | 99.99% | 52m 36s | 4m 23s |
| Five nines | 99.999% | 5m 15s | 26s |

### Sequential vs Parallel Availability

**Sequential :** components in a chain — overall availability **drops**

> Total = A × B
Two × 99.9% in sequence → **99.8%**
> 

**Parallel :** redundant components — overall availability **rises**

> Total = 1 − (1 − A)(1 − B)
Two × 99.9% in parallel → **99.9999%**
> 

### How Parallel Design Works in Practice

Three implementation layers:

1. **Load Balancer** — distributes traffic across multiple servers; if one fails, traffic reroutes automatically
2. **Multi-AZ Deployment** — services run across multiple data centers or regions; a regional failure doesn't affect others
3. **Database Replication** — multiple copies of data; if the primary fails, a replica takes over

> **Key principle:** Parallel design requires two nodes to fail *simultaneously* to cause an outage — making failures exponentially less likely.
>

## 1. DNS (Domain Name System)

### How DNS Resolution Works

DNS translates human-readable domain names into IP addresses — the internet's "phone book."

**Resolution flow:**

1. Browser checks local cache (browser → OS → router)
2. Query sent to **Local DNS Resolver** (provided by ISP)
3. Local DNS queries **Root DNS Server** → directed to TLD server
4. **TLD DNS Server** (.com, .cn) → directed to authoritative server
5. **Authoritative DNS Server** returns the actual IP address
6. Result cached at every level, controlled by **TTL (Time To Live)**

### DNS Record Types

| Record | Full Name | Purpose | Example |
| --- | --- | --- | --- |
| **A** | Address | Domain → IPv4 address | `google.com → 142.250.x.x` |
| **CNAME** | Canonical Name | Domain → another domain | `www.google.com → google.com` |
| **NS** | Name Server | Which DNS server is authoritative | `google.com → ns1.google.com` |
| **MX** | Mail Exchange | Which server handles email | `@google.com → smtp.google.com` |

### DNS Routing Strategies

- **Weighted Round Robin** — distribute traffic by weight; useful for A/B testing and canary releases
- **Latency-based** — return the IP with the lowest latency for the user's location
- **Geolocation-based** — route users to region-specific servers (e.g. Chinese users → China servers)

### Disadvantages

- Slight lookup latency (mitigated by caching)
- DNS changes don't propagate instantly — TTL delay (Eventual Consistency)
- DNS servers can be targeted by DDoS attacks

## 2. CDN (Content Delivery Network)

### What It Does

A globally distributed network of proxy servers that caches static content (HTML, CSS, JS, images, video) at nodes close to users.

**Two core benefits:**

- Users fetch content from the nearest node → faster load times
- Reduces load on the origin server

### Push CDN vs Pull CDN

|  | Push CDN | Pull CDN |
| --- | --- | --- |
| How it works | Owner pushes content to CDN nodes proactively | CDN fetches from origin on first request, then caches |
| Best for | Small traffic, infrequently updated content | High traffic, frequently changing content |
| Advantage | Nodes always have the latest content | Saves storage; only caches what's actually requested |
| Disadvantage | Uses more storage space | First request is slow (cache miss → origin fetch) |

### Disadvantages

- Can be expensive (billed by traffic volume)
- Content may be stale if TTL hasn't expired when updates are pushed
- Requires static asset URLs to point to CDN domain

---

## 3. Load Balancer

### What It Does

Distributes incoming requests across multiple backend servers to prevent overload and eliminate single points of failure.

**Core benefits:**

- Prevents requests from hitting unhealthy servers (via health checks)
- Prevents any single server from being overloaded
- Eliminates single point of failure (SPOF)
- Enables SSL termination and session persistence

### L4 vs L7 Load Balancing

|  | L4 (Transport Layer) | L7 (Application Layer) |
| --- | --- | --- |
| Operates on | IP address + port | HTTP headers, URL, cookies |
| Reads content? | No | Yes |
| Method | Forwards packets (NAT) | Terminates and re-establishes connection |
| Performance | Faster, lower overhead | Slightly higher overhead |
| Use cases | Databases, game servers, high-throughput TCP | Web apps, API gateways, microservices |
| Example routing | Port 443 → HTTPS servers | `/api/*` → API servers, `/video/*` → video servers |

### Routing Algorithms

| Algorithm | Description | Best for |
| --- | --- | --- |
| Round Robin | Rotate through servers in order | Similar server specs |
| Weighted Round Robin | Route by assigned weight | Different server capacities |
| Least Connections | Send to server with fewest active connections | Variable request durations |
| Random | Pick randomly | Simple, uniform workloads |
| Session / Cookie | Same user always hits same server | Stateful applications |

### Horizontal vs Vertical Scaling

|  | Horizontal Scaling (Scale Out) | Vertical Scaling (Scale Up) |
| --- | --- | --- |
| Method | Add more servers | Upgrade CPU/RAM on one server |
| Cost | Lower, commodity hardware | Higher, diminishing returns |
| Ceiling | Virtually unlimited | Hard hardware limit |
| Enabled by | Load Balancer | N/A |

### Disadvantages

- Load balancer itself can become a bottleneck
- A single load balancer is a SPOF → deploy multiple LBs (Active-Passive or Active-Active)
- Increases system complexity

---

## 4. Reverse Proxy

### What It Does

A server that sits in front of backend servers and handles all client communication. Clients never contact backend servers directly.

**Capabilities:**

- **Security** — hides backend topology; supports IP whitelisting, rate limiting
- **SSL termination** — handles HTTPS at the proxy; backend only needs HTTP
- **Compression** — compresses responses to reduce bandwidth
- **Caching** — serves cached responses without hitting the backend
- **Static content** — serves HTML, CSS, JS, images directly

### Reverse Proxy vs Load Balancer

| Dimension | Reverse Proxy | Load Balancer |
| --- | --- | --- |
| Primary purpose | Security, caching, SSL, compression | Distribute traffic across multiple servers |
| Value with 1 backend server | ✅ Yes — still useful | ❌ No — no traffic to distribute |
| Representative tools | Nginx, HAProxy | Nginx, HAProxy, AWS ELB |

> **Note:** Nginx and HAProxy can act as both simultaneously.
> 

### Disadvantages

- Adds system complexity
- Single reverse proxy is a SPOF → deploy multiple with failover

---

## 5. Single Point of Failure (SPOF) Analysis

For a typical chain: **User → DNS → CDN → Load Balancer → App Servers (×3)**

| Component | SPOF Risk | Solution |
| --- | --- | --- |
| DNS | ✅ Low — inherently redundant (multiple NS records) | Configure multiple NS records |
| CDN | ⚠️ Medium — a node failure affects regional users | Auto-failover to next nearest node; fallback to origin |
| Load Balancer | 🔴 High — single LB failure = full outage | Deploy multiple LBs (Active-Passive or Active-Active) |
| App Servers ×3 | ✅ Low — already parallel; LB health checks reroute traffic | Health checks + automatic node removal |
| Database (not in chain) | 🔴 Highest — single DB failure = full data loss risk | Master-Slave replication + automatic failover *(Batch 5)* |

> **Key principle:** The goal is to eliminate every SPOF in the chain. Parallel (redundant) design at each layer compounds into extremely high overall availability.
>

## 1. Application Layer

### Monolith → Layered Architecture

Early systems ran web logic and business logic on the same server. As scale grows, the first evolution is separating the **Web Layer** from the **Application Layer**.

**Web Layer** — handles HTTP, routing, static assets
**Application Layer** — handles business logic, computation, API responses
**Data Layer** — databases, caches

**Benefits of separation:**

- Each layer scales **independently** — scale only the application layer when business logic is the bottleneck
- Each layer deploys **independently** — lower release risk
- Foundation for further decomposition into microservices

### Stateless Application Layer

The application layer must be **stateless** — it stores no session or user state locally. Sessions are stored in an external cache (e.g. Redis). This allows any application server to handle any request, enabling **free horizontal scaling**.

---

## 2. Microservices

### Definition

A further decomposition of the application layer. A large application is split into small, **independently deployable services**, each responsible for one business capability, communicating via APIs.

### Core Characteristics

- **Single Responsibility** — each service does one thing; clear boundaries
- **Independent Deployment** — update one service without restarting others
- **Independent Scaling** — scale only the service under pressure
- **Technology Heterogeneity** — each service can use a different language or stack
- **Decentralized Data** — each service owns its own database; no shared DB

### Why Independent Databases?

- Reduces coupling — one service's schema changes don't break others
- Each service can iterate and deploy without affecting the rest
- Allows each service to choose the best database type for its needs

### Trade-offs

| Advantages | Disadvantages |
| --- | --- |
| Small, independent deployments = lower risk | Network calls between services = added latency |
| Independent scaling = better resource efficiency | Distributed transactions are hard |
| Flexible tech stack per service | Operational complexity increases significantly |
| Fault isolation — one service failing doesn't take down all | Service dependency tracing is difficult |
| Teams can develop in parallel | Requires mature monitoring and logging |

> **Key insight:** Microservices are not a silver bullet. Small teams and early-stage products are almost always better served by a monolith first. Microservices make sense when the business is complex, the team is large, and independent scaling is genuinely needed.
> 

---

## 3. Service Discovery

### Why It's Needed

In a microservice environment, service instances have dynamic IPs that change constantly (container restarts, auto-scaling). Hardcoding IPs is not viable. Service discovery answers the question: **"How does Service A find Service B?"**

### Two Discovery Patterns

|  | Client-side Discovery | Server-side Discovery |
| --- | --- | --- |
| How it works | Client queries the registry directly, then calls the target | Client sends request to a router; router queries registry and forwards |
| Load balancing | Done by the client | Done by the router |
| Client complexity | High — must implement LB logic | Low — client is unaware of service locations |
| Extra network hop | No | Yes |
| Example | Netflix Eureka | AWS ELB + Consul |

### Two Registration Approaches

- **Self-registration** — service instance registers and maintains its own heartbeat. Simple, but couples service code to the registry.
- **Third-party registration** — external system (e.g. Kubernetes) monitors instances and registers them. Service code has no awareness of the registry — cleaner separation.

---

## 4. Service Registry Tools

|  | Consul | Etcd | Zookeeper |
| --- | --- | --- | --- |
| Consensus algorithm | Raft | Raft | ZAB (Paxos-like) |
| Built-in health checks | ✅ Native | ❌ Must implement | ❌ Must implement |
| Interface | HTTP + DNS | gRPC / HTTP | Proprietary SDK |
| Operational complexity | Medium | Lowest | Highest |
| Primary ecosystem | General microservices | Kubernetes core | Kafka / Hadoop |

### Why Each Tool Wins Its Niche

**Consul** — supports DNS-based service lookup out of the box (`user-service.service.consul`), plus health checks and KV config storage in one package. Lowest integration cost for existing systems.

**Etcd** — powers Kubernetes because it provides extreme consistency guarantees and a **Watch mechanism** (instantly notifies subscribers when a key changes — the foundation of Kubernetes scheduling). Lightweight and focused on doing one thing well.

**Zookeeper** — mature and battle-tested in the Hadoop/Kafka ecosystem. Being gradually replaced in new projects by Etcd and Consul due to JVM dependency, complex client API, and steeper learning curve. Still deeply embedded in legacy big data stacks.

Relational databases store data in tables linked by foreign keys. Core products: MySQL, PostgreSQL, Oracle, SQL Server.

### ACID Properties

| Letter | Property | Meaning | Example |
| --- | --- | --- | --- |
| **A** | Atomicity | All operations in a transaction succeed or all roll back — no partial state | Debit and credit happen together or not at all |
| **C** | Consistency | The database moves from one valid state to another; all constraints hold | Account balance cannot go negative |
| **I** | Isolation | Concurrent transactions don't interfere; result equals serial execution | Two simultaneous purchases of the last item are handled correctly |
| **D** | Durability | Committed data survives crashes and power failures | Order exists after a server restart |

> ⚠️ **ACID-C vs CAP-C — critical distinction:**
> 
> - **ACID Consistency** = data doesn't violate business constraints (e.g. balance ≥ 0)
> - **CAP Consistency** = all distributed nodes see the same data at the same time
> These are completely different concepts. Don't confuse them in interviews.

## 2. Scaling Techniques Overview

Five techniques for scaling relational databases, in increasing order of complexity:

| Technique | Splits by | Solves | Primary Limitation |
| --- | --- | --- | --- |
| Master-Slave | — | Read throughput | Write still single point |
| Master-Master | — | Write availability | Write conflict complexity |
| Federation | Business domain | Independent domain scaling | Cross-domain joins impossible |
| Sharding | Data rows | Unlimited horizontal scale | Resharding cost, cross-shard queries |
| Denormalization + SQL Tuning | — | Query speed without architecture change | Write overhead, consistency cost |

---

## 3. Master-Slave Replication

**How it works:** One Master handles all writes. Data is asynchronously replicated to one or more Slaves. Slaves handle reads only.

**Advantages:**

- Read performance scales linearly with number of Slaves
- Slaves serve as hot backups; can be promoted to Master on failure

**Disadvantages:**

- Write throughput is still limited to one Master (single point for writes)
- **Replication Lag** — async replication means Slaves may return stale data immediately after a write
- Master failure requires manual or automated promotion; brief downtime possible, uncommitted data may be lost

---

## 4. Master-Master Replication

**How it works:** Two or more Masters all handle reads and writes. They sync bidirectionally. A Load Balancer distributes traffic across Masters.

**Advantages:**

- Write throughput scales across multiple Masters
- High availability — no single point of failure

**Disadvantages:**

- **Write conflicts** — two Masters modifying the same row simultaneously require a conflict resolution strategy (timestamp, business rules, etc.)
- Weaker consistency than Master-Slave
- Significantly higher operational complexity

---

## 5. Federation (Functional Partitioning)

**How it works:** Split one large database into multiple independent databases by **business domain**. Each database owns one functional area.

**Example:** `users_db` / `orders_db` / `products_db` / `payments_db`

**Advantages:**

- Smaller databases → smaller indexes → higher cache hit rate
- Each database scales and deploys independently
- Writes are parallelized across domains; higher overall write throughput
- One domain's failure doesn't affect others

**Disadvantages:**

- Cross-domain JOINs must be done at the application layer (complex)
- Cross-domain ACID transactions are not feasible
- Application layer must route writes to the correct database
- Doesn't solve the problem of one domain growing too large (e.g. 1 billion users in `users_db`)

---

## 6. Sharding (Horizontal Partitioning)

**How it works:** Split the **rows** of a single table across multiple database nodes. Each node (shard) holds a subset of the data. A Shard Router directs requests to the correct shard based on the **Shard Key**.

**Example:** Users table with 100M rows split into 4 shards by user ID range.

### Shard Key Selection — Critical Decision

| Shard Key | Distribution | Risk |
| --- | --- | --- |
| Timestamp | New shard always hottest | 🔴 Severe hot spot |
| Geography | High-population regions overloaded | 🟡 Uneven distribution |
| **Hash(user_id)** | Uniform across all shards | ✅ Recommended |

**Hash formula:** `shard_id = hash(user_id) % number_of_shards`
The hash function maps any input to a uniformly distributed output — regardless of ID value or age, data lands on a random shard.

**Disadvantages:**

- **Hot spots** — poor shard key choice concentrates data on one shard
- **Cross-shard queries** — joins across shards require application-level result merging
- **Resharding** — adjusting shard strategy as data grows is extremely costly
- **Cross-shard transactions** — ACID cannot be guaranteed; distributed transactions required (very expensive)

---

## 7. Denormalization

**Normalization** — eliminate redundancy; data stored once; relationships via JOINs. Clean design but slow JOINs at scale.

**Denormalization** — intentionally introduce redundancy by storing pre-joined data together. Trade storage space for read speed.

**Example:** Instead of JOINing `orders + users + products` on every query, store `user_name` and `product_name` directly in the `orders` table.

**Advantages:** Read queries are very fast — no JOINs needed

**Disadvantages:**

- Write operations must update redundant data in multiple places
- Data consistency is harder to maintain
- Increased storage usage

> **When to apply:** After Federation and Sharding make JOINs impractical or impossible across nodes. Not a first resort.
> 

---

## 8. SQL Tuning

Performance optimization at the query level — no architectural changes required.

| Technique | Description | Impact |
| --- | --- | --- |
| **Indexing** | Add indexes on WHERE, JOIN ON, ORDER BY columns | Converts O(n) full scan to O(log n) lookup — highest ROI |
| **Avoid SELECT *** | Only retrieve needed columns | Reduces network transfer and memory usage |
| **EXPLAIN** | Analyze query execution plan to identify full scans and bad joins | Diagnoses root causes |
| **Partitioning** | Split large tables into partitions within one database; queries scan only relevant partitions | Reduces scan volume |
| **Batch operations** | Combine multiple single-row INSERTs into one batch INSERT | Reduces network round tri |

## 1. Why NoSQL Emerged

Relational databases were designed in the 1970s — before the internet existed. When companies like Google, Amazon, and Facebook faced **billions of users, petabytes of data, and global distribution**, RDBMS limitations became critical:

- Fixed schema — costly to change as business evolves rapidly
- Vertical scaling ceiling — single machine has a hard performance limit
- Poor JOIN performance at massive scale
- Strong ACID consistency is expensive in distributed environments

**NoSQL (Not Only SQL)** trades some ACID guarantees for better scalability, flexibility, and performance.

---

## 2. BASE Principles

NoSQL's theoretical foundation — the counterpart to ACID:

| Letter | Full Name | Meaning | ACID Contrast |
| --- | --- | --- | --- |
| **BA** | Basically Available | System remains available even if some nodes fail | vs. full Availability guarantee |
| **S** | Soft State | System state may be temporarily inconsistent | vs. strict Consistency |
| **E** | Eventual Consistency | Data will converge to a consistent state over time | vs. immediate Consistency |

> **Core idea:** Give up strong consistency in exchange for higher availability and partition tolerance — the AP choice in CAP theorem.
> 

---

## 3. Four NoSQL Types

NoSQL is not one database — it is four fundamentally different database categories, each solving a different problem.

---

### 3.1 Key-Value Store

**Data model:** A key maps directly to a value (string, number, JSON, binary). The database treats the value as opaque — it cannot query inside it.

**Core characteristics:**

- O(1) read/write — direct key lookup, no scanning
- No schema — value structure is completely free
- Usually in-memory — 100x faster than disk

**Use cases:**

- Session storage (Key = SessionID, Value = user info)
- Caching database query results
- Real-time leaderboards (Redis Sorted Set)
- Atomic counters (likes, view counts)
- Distributed locks (Redis SETNX)

**Products:** Redis (rich data structures, optional persistence), DynamoDB (AWS managed, infinite scale), Memcached (pure cache, no persistence)

**Limitations:** Can only query by key; no filtering by value fields; no complex queries or JOINs

---

### 3.2 Document Store

**Data model:** Data stored as structured documents (JSON/BSON). Documents can be nested. Unlike Key-Value, the database understands the document's internal fields and can query any of them.

```json
{
  "_id": "order_001",
  "user": {"id": 1001, "name": "Alice"},
  "items": [{"product": "iPhone", "price": 999}],
  "status": "shipped"
}
```

**Use cases:**

- Content management systems (articles, blogs with varied fields)
- E-commerce product catalogs (different attributes per category)
- User preference profiles
- Real-time event logging

**Products:** MongoDB (most popular, rich aggregation), CouchDB (offline sync, mobile-friendly), Elasticsearch (full-text search specialist)

**Limitations:** No cross-document JOINs (must merge at application layer); weak transaction support; data redundancy from nesting

---

### 3.3 Wide Column Store

**Data model:** Rows addressed by a **Row Key**; each row can have different columns; columns are grouped into **Column Families** stored contiguously on disk.

**Key structural feature:** Sparse storage — missing columns take no space. Each row can have millions of different columns.

**Why writes are extremely fast:** Data is written **sequentially by column family** on disk. Sequential writes are 10–100x faster than random writes (which RDBMS requires for row updates).

**Use cases:**

- Time-series data (sensor readings, stock prices) — Row Key = deviceID + timestamp
- IoT data — millions of writes per second
- User behavior logs — massive write volume, time-range queries
- Fan/follower lists — Row Key = userID, each column = one follower ID (supports billions of columns per row)

**Products:** Cassandra (AP system, no SPOF, linear scaling, global distribution), HBase (CP system, built on HDFS, deep Hadoop integration), Google Bigtable (the original, ancestor of both)

**Limitations:** No JOINs or complex multi-condition queries; Row Key design is critical — poor design kills performance; steep learning curve

---

### 3.4 Graph Database

**Data model:** **Nodes** (entities: people, products, places) connected by **Edges** (relationships: knows, bought, located-in). Both nodes and edges carry properties.

**Why it outperforms RDBMS for relationship queries:**
In SQL, each additional relationship hop requires another JOIN — complexity grows exponentially. Graph databases store relationships as **direct pointers**; traversing edges requires no JOINs — deep relationship queries run orders of magnitude faster.

**Use cases:**

- Social networks — friend recommendations, mutual connections
- Recommendation engines — "people who bought X also bought Y"
- Fraud detection — identifying linked account networks
- Knowledge graphs — entity relationship reasoning
- Route planning — shortest path algorithms

**Products:** Neo4j (most mature, Cypher query language), Amazon Neptune (managed, supports Gremlin and SPARQL)

**Limitations:** Poor fit for massive simple data storage and high-volume writes; full-graph traversal algorithms are memory-intensive; ecosystem less mature than RDBMS

---

## 4. SQL vs NoSQL Selection Guide

### Decision Framework

| Business Requirement | Choose |
| --- | --- |
| Strict ACID transactions (payments, orders, inventory) | **SQL** (MySQL, PostgreSQL) |
| Ultra-fast key-based access, caching, sessions | **Key-Value** (Redis) |
| Flexible schema, varied document structures, full-text search | **Document** (MongoDB, Elasticsearch) |
| Massive write throughput, time-series, IoT, fan lists | **Wide Column** (Cassandra) |
| Deep multi-hop relationship queries, recommendations, fraud | **Graph** (Neo4j) |

### Key Principles

**Real systems always use multiple databases** — each handles what it does best:

- Orders → SQL (ACID transactions)
- Sessions → Redis (speed)
- Product search → Elasticsearch (full-text)
- Activity logs → Cassandra (write throughput)
- Recommendations → Neo4j (relationship traversal)

**Wide Column vs Document — core distinction:**

- Document: read/write complete structured documents; best for flexible queries on varied data
- Wide Column: sequential column-family writes to disk; best for extreme write throughput and time-series data

**Graph vs Wide Column — what each cannot do:**

- Graph: poor at storing massive volumes of simple data (logs, time-series) — graph traversal is memory-intensive
- Wide Column: poor at complex multi-field filtering — efficient only when querying by Row Key

## 1. Why Caching Matters

| Storage | Latency |
| --- | --- |
| Disk read | ~10ms |
| Memory read | ~100μs |
| **Difference** | **~100x** |

Caching keeps hot data in memory to avoid repeated disk reads. Benefits: lower DB load, lower response latency, higher throughput.

---

## 2. Five Cache Locations

| Layer | Location | Example |
| --- | --- | --- |
| ① | **Client Cache** | Browser HTTP cache, Cache-Control, ETag |
| ② | **CDN Cache** | Static assets cached at nodes nearest to users |
| ③ | **Web Server Cache** | Reverse proxy cache (Nginx, Varnish) |
| ④ | **Application Cache** | Distributed cache — Redis, Memcached |
| ⑤ | **Database Cache** | Query cache, Buffer Pool |

> Architects most commonly work at layer ④. All four cache strategies below operate at this level.
> 

---

## 3. Four Cache Strategies

### Cache-aside (Lazy Loading)

The most common strategy. The application manages the cache directly.

**Read flow:**

1. Check cache first
2. **Cache hit** → return immediately
3. **Cache miss** → query database → write result back to cache → return

**Write flow:** Write to database first → **invalidate** the cache entry (do not update it). Next read will reload from DB.

**Best for:** Read-heavy workloads (read:write ratio 10:1 or higher)
**Trade-off:** First read after miss has extra latency; brief inconsistency window between cache and DB

---

### Write-through

Every write updates **both cache and database synchronously** before returning.

**Flow:** App writes → cache updated → DB updated synchronously → return

**Advantages:** Cache and DB always consistent; reads always hit cache with accurate data
**Disadvantages:** Write latency increases (must wait for two operations); wastes cache memory if written data is rarely read

**Best for:** Read-write balanced workloads where consistency is critical

---

### Write-behind (Write-back)

Writes go to cache only and return immediately. Cache asynchronously flushes to database in batches.

**Flow:** App writes → cache updated → return immediately → cache flushes to DB asynchronously

**Advantages:** Extremely high write performance (memory-only); batch writes reduce DB pressure; multiple writes to same key can be merged
**Disadvantages:** Cache crash = uncommitted data **permanently lost**; higher implementation complexity

**Best for:** Write-intensive workloads where minor data loss is acceptable (game scores, real-time counters)

---

### Refresh-ahead

Cache entries are **proactively refreshed before they expire**. Users never experience a cache miss on hot data.

**Flow:** Cache TTL = 10 min → at minute 8, system asynchronously pre-fetches fresh data from DB → user at minute 10 gets fresh data with zero miss latency

**Advantages:** Zero miss latency for hot data; no latency spikes from expiry
**Disadvantages:** Wasted resources if predicted hot data isn't actually accessed; higher implementation complexity

**Best for:** Predictable hot data access patterns (homepages, trending lists, leaderboards)

---

### Strategy Comparison

| Strategy | Read Perf | Write Perf | Consistency | Best For |
| --- | --- | --- | --- | --- |
| Cache-aside | High (after hit) | Medium | Briefly inconsistent | Read-heavy |
| Write-through | High (always hits) | Low (sync wait) | Strong | Balanced read/write |
| Write-behind | High | Very High | Weak (loss risk) | Write-heavy, loss-tolerant |
| Refresh-ahead | Highest (no miss) | Medium | Briefly inconsistent | Predictable hot data |

## 4. Three Cache Failure Modes

### Cache Penetration（缓存穿透）

**Problem:** Querying data that doesn't exist in either cache or DB. Every request bypasses cache and hits DB.
**Cause:** Malicious requests or bugs querying non-existent keys
**Solutions:**

- **Bloom Filter** — probabilistically check if key exists before querying
- **Cache null values** — cache a null/empty result with a short TTL

### Cache Avalanche（缓存雪崩）

**Problem:** Large numbers of cache keys expire simultaneously (or cache server goes down). All traffic floods the DB at once.
**Cause:** Same TTL set for all keys; cache server failure
**Solutions:**

- **Add random jitter to TTL** — e.g. TTL = 10min + random(0-2min) to stagger expiry
- **Multi-level cache** — L1 local cache + L2 Redis; DB only hit if both miss
- **Circuit breaker** — automatically reject requests when DB is overloaded

### Cache Breakdown（缓存击穿）

**Problem:** A single highly-requested hot key expires. Thousands of concurrent requests simultaneously miss cache and hammer DB.
**Cause:** Hot key TTL expiry under high concurrency
**Solutions:**

- **Mutex lock** — only one request rebuilds the cache; others wait
- **Never-expire hot keys** — logically expire via application logic, not TTL

## 5. Asynchronous Processing

Caching improves read performance. Async processing removes slow operations from the request path so users get immediate responses.

### Message Queue

**Core concept:** Producers publish messages to a queue; consumers process them asynchronously. The two sides are decoupled.

**Three core values:**

- **Decoupling** — producer doesn't know who consumes; consumer doesn't know who produces
- **Traffic shaping (削峰)** — messages buffer in queue during traffic spikes; consumers process at their own pace
- **Async** — users get immediate responses without waiting for downstream operations

**What to make sync vs async:**

- **Sync** — operations the user must wait for before proceeding (e.g. "order confirmed")
- **Async** — everything else: sending email, updating inventory, triggering recommendations

**Products:** Kafka (high throughput, durable, log streaming), RabbitMQ (flexible routing, low latency), AWS SQS (managed, simple, reliable)

---

### Task Queue

A specialization of message queues focused on **executing discrete units of work**.

|  | Message Queue | Task Queue |
| --- | --- | --- |
| Carries | Events / notifications ("what happened") | Work units ("what to do") |
| Consumer action | React to event | Execute a task |
| Example | "Order placed" triggers email + inventory + recommendations | Convert uploaded video to MP4 |

**Products:** Celery (Python), Sidekiq (Ruby), Bull (Node.js)

---

### Back Pressure

**Problem without back pressure:** Producer sends faster than consumer can process → queue grows unbounded → memory exhausted → system crashes → all data lost.

**Back pressure mechanism:** When queue depth exceeds a threshold, the system **signals the producer to slow down or pause**, keeping the system stable under load.

**With back pressure:**

- Requests may be slower or queued — users may see "processing" state
- System remains stable and recovers when load decreases
- No data loss

> **Core principle:** It is always better to respond slowly than to crash. Back pressure is a system's self-protection mechanism under extreme load.

## 1. TCP vs UDP

| Dimension | TCP | UDP |
| --- | --- | --- |
| Connection | Connection-oriented (3-way handshake) | Connectionless |
| Reliability | ✅ Guaranteed delivery (retransmission) | ❌ Best-effort |
| Ordering | ✅ In-order delivery | ❌ May arrive out of order |
| Speed | Slower (handshake + ACK overhead) | ✅ Fast (no handshake) |
| Use cases | HTTP, file transfer, email, payments | Video streaming, games, DNS |

**TCP 3-way handshake:** SYN → SYN-ACK → ACK

**Selection rule:**

- Data must not be lost → **TCP**
- Speed matters more than completeness → **UDP**

## 2. RPC (Remote Procedure Call)

**Concept:** Call a function that executes on a remote server. The network transport is transparent to the caller — it looks like a local function call.

**Flow:**

1. Client calls local stub
2. Stub **serializes** parameters (e.g. Protocol Buffers → binary)
3. Binary sent over network
4. Server stub **deserializes** → executes actual function
5. Result serialized and returned the same way

**Key frameworks:** gRPC (Google, HTTP/2 + Protocol Buffers, very high performance), Thrift (Facebook)

**Best for:** Internal microservice-to-microservice communication; both sides owned by same team; performance-critical paths

---

## 3. REST (Representational State Transfer)

**Concept:** An HTTP-based API style that treats everything as a **resource** operated on with standard HTTP verbs.

### Six Constraints

| Constraint | Meaning |
| --- | --- |
| **Stateless** | Each request contains all necessary info; server stores no client state |
| **Uniform Interface** | Standard HTTP verbs (GET/POST/PUT/DELETE) on resources |
| **Resource Identification** | Every resource has a unique URL (e.g. `/users/1001`) |
| **Cacheable** | Responses can be cached by client or intermediaries |
| **Layered System** | Client doesn't know if it's talking to a server or proxy |
| **Code on Demand** (optional) | Server can send executable code to client |

### HTTP Verbs

| Verb | Operation | Example |
| --- | --- | --- |
| GET | Read | `GET /users/1001` |
| POST | Create | `POST /users` |
| PUT | Full update | `PUT /users/1001` |
| PATCH | Partial update | `PATCH /users/1001` |
| DELETE | Delete | `DELETE /users/1001` |

---

## 4. RPC vs REST

| Dimension | RPC | REST |
| --- | --- | --- |
| Abstraction | Function call | Resource operation |
| Performance | High (binary protocol) | Medium (JSON text) |
| Coupling | High (shared interface definition) | Low (standard HTTP, universal) |
| Best for | Internal microservice communication | Public-facing APIs |

> **In practice:** Systems often use both — RPC between internal services, REST for external APIs.

## 5. Security Fundamentals

Security must be designed in from the start, not bolted on afterward.

### Seven Core Principles

**1. Encryption in Transit**
All network communication over HTTPS (TLS). Prevents man-in-the-middle attacks and eavesdropping.

**2. Encryption at Rest**
Sensitive data encrypted in storage. Passwords must use slow hash algorithms (bcrypt, Argon2) — never plaintext, never MD5/SHA1.

**3. Principle of Least Privilege**
Every service, user, and process gets only the minimum permissions needed. DB accounts should not have DROP TABLE.

**4. Input Validation**
All user input must be validated and sanitized. Use parameterized queries — never concatenate SQL strings.

**5. Authentication vs Authorization**

|  | Authentication (AuthN) | Authorization (AuthZ) |
| --- | --- | --- |
| Question | Who are you? | What can you do? |
| Method | Password, Token, OAuth | RBAC, ACL |
| When | At login | Before every operation |

**6. Rate Limiting**
Limit requests per IP/user per time window. Prevents brute-force attacks and DDoS.

**7. Common Attack Defenses**

| Attack | Defense |
| --- | --- |
| SQL Injection | Parameterized queries, ORM |
| XSS | Output escaping, Content Security Policy |
| CSRF | CSRF tokens, SameSite cookies |
| DDoS | CDN, Rate limiting, WAF |

## 6. Reference Numbers

### Latency Numbers Every Architect Should Know

| Operation | Latency |
| --- | --- |
| L1 Cache read | ~0.5 ns |
| L2 Cache read | ~7 ns |
| Main memory (RAM) read | ~100 ns |
| SSD random read | ~150 μs |
| Same datacenter network round trip | ~0.5 ms |
| HDD sequential read 1MB | ~20 ms |
| Cross-continental network round trip | ~150 ms |

**Key insights:**

- Memory is ~1,000x faster than disk → justifies caching
- Same DC is ~300x faster than cross-continental → justifies geographic distribution

## 7. System Design Interview — 4-Step Framework

### Step 1: Clarify Requirements (~5 min)

- **Functional:** What are the core features? Number of users? Read/write ratio?
- **Non-functional:** Availability target? Latency requirement? Consistency level?
- **Scope:** What is explicitly out of scope?

### Step 2: Capacity Estimation (~5 min)

- **QPS:** DAU × requests per user per day
- **Storage:** Record size × daily new records × retention years
- **Bandwidth:** QPS × average response size

### Step 3: High-Level Design (~15 min)

- Draw core components: Client → LB → Service → DB → Cache
- Define primary data flows and API interfaces
- Get the system working first, then optimize

### Step 4: Deep Dive (~20 min)

- Identify bottlenecks: what breaks first under load?
- Discuss database selection, caching strategy, sharding approach
- **Articulate trade-offs:** explain why you chose this, and what you're giving up

> **Key mindset:** There are no perfect answers — only well-reasoned trade-offs. Say what you chose and why, acknowledge the costs.

## 8. Case Studies

### URL Shortener (e.g. bit.ly)

| Problem | Decision | Reason |
| --- | --- | --- |
| Short URL generation | Base62 encoding + auto-increment ID | Guaranteed unique, controllable length |
| Database | SQL (writes) + Redis (read cache) | Writes need transactions; reads need speed |
| Access pattern | Cache-aside on reads | 100:1 read/write ratio → high cache hit rate |

### Twitter Feed (Timeline)

|  | Pull Mode | Push Mode (Fan-out) |
| --- | --- | --- |
| How | Aggregate followed users' tweets on request | Push new tweet to every follower's feed cache |
| Read speed | Slow (real-time aggregation) | Fast (read from cache) |
| Write speed | Fast | Slow (1M follower fan-out is expensive) |
| Celebrity problem | None | Fan-out to millions is prohibitively costly |

**Twitter's actual solution — Hybrid:**

- Regular users → Push; pre-computed feed stored in Redis
- Celebrities (>1M followers) → Pull; mixed in at read time

> This is the purest real-world expression of **"Everything is a trade-off."**
